## The bytes

```
0x00c05bec  8b 7d dc                 mov edi, dword ptr [ebp - 0x24]   <-- separate index entry, size 3
0x00c05bef  57                       push edi                          <-- this entry, size 8
0x00c05bf0  e8 05 20 00 00           call 0x00c07bfa
0x00c05bf5  59                       pop ecx
0x00c05bf6  c3                       ret
0x00c05bf7  8b 4c 24 04              mov ecx, dword ptr [esp + 4]      <-- next function starts
```

`0x00c05bef` begins **three bytes into** a sequence that belongs to the enclosing function, and the
enclosing function at `0x00c05bde` does `call 0x00c05bef` — i.e. the address is a **funclet**: a
compiler-generated EH/cleanup fragment that other code calls into, with `edi` already holding the
value. It is not a C++ function entry.

## Why no source can match it

The only C++ shape that reaches that call is a one-argument forwarder, and it compiles to a tail
call (measured, `f3check`, check 1):

```
ORIG   push edi / call FUN_00c07bfa / pop ecx / ret      (8 bytes)
OURS   jmp  FUN_00c07bfa                                 (5 bytes)
```

A `__cdecl` parameter lives at `[esp+4]`, so even when the tail call is suppressed the pushed
operand is `[esp+4]`, never `edi`. `push edi` as the *first* instruction requires the argument to
arrive in `edi`, which happens only in funclet glue — nothing expressible in the unit's source can
produce it. Acquiring it would need the index entry to point at the enclosing function's real entry
(`0x00c05b7f`-ish), not at this fragment.
