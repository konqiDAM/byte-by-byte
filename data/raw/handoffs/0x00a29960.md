## The residue, re-measured exactly (ebp-normalised, not raw `[esp+N]`)

Raw `[esp+N]` cannot be compared across instructions (pushes move esp by 4/8/12). The tool
`work_a29960b\slotdiff.py` tracks push/pop/sub/add esp and reports ebp-relative offsets:

| local | ORIGINAL | ours |
|---|---|---|
| `record` | -80 | -80 |
| `copiedEnums` | -76 | -76 |
| **`name`** | **-72** | -56 |
| **`flags`** | **-68** | -72 |
| **`copiedDefaults`** | **-64** | -68 |
| **`copiedMembers`** | **-56** | -64 |
| `parent` / `destination` | -64 / -56 | -64 / -56 |
| `input, enumField … interfacesField` | -48 … -8 | -48 … -8 |

**Both builds use the same four slots {-72,-68,-64,-56}.** It is one rotation of the same assignment,
not a different pool size: both order the four as `flags → copiedDefaults → copiedMembers → name`
(ours) and the original starts the same cycle at `name`. `-64` and `-56` are the recycled slots of
`parent` (dies 0xb1) and `destination` (dies 0x92); `-72`,`-68` are the fresh pair. In our build the
two recycled slots go to the last two in processing order (`copiedMembers`, `name`); in the original
they go to `copiedDefaults` and `copiedMembers`.

Our build's pool order = **reverse definition order** (flags 0x1cc, cd 0x183, cm 0x161, name 0xd7),
with `record`/`copiedEnums` pinned at the front (-80,-76). The original's order is `name, flags, cd,
cm` — which matches no order derivable from the (byte-identical) instruction stream, so the lever
must be a source construct that changes lives/numbering while emitting the same code.
