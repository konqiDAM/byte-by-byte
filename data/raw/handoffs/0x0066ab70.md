# 0x0066ab70 — INDEX DEFECT: the pack span swallows the NEXT function

Claim `clm_1246189f93ed4740a587` (released 2026-11-12, best_code kept). **Do not re-claim expecting a match.**

## The finding

`pack.json` says `size: 409`. The real function is **384 bytes**.

`rivals/0x0066ab70/best.cpp` scores `status=wip ndiff=0 extent=384 errs=2` — **zero instruction
differences in the overlap** — and the checker reports:

```
compiled function extent differs: 384 vs 409
compiled section shorter than original function
```

`exp91\dump_tail.py claims\<cid> 0x160 0x199` shows why. The layout is:

```
+0x000 .. +0x16b   the function (code)
+0x16e  mov edi,edi              alignment
+0x170  4 dwords -> 0x66ab90, 0x66ab90, 0x66ac26, 0x66ac26    the switch jump table
+0x180  ==> a DIFFERENT FUNCTION <==
```

and the bytes at `+0x180` are a complete, separate entry point with its own `ret 8`:

```
180  32 c0            xor  al, al
182  83 7c 24 04 0a   cmp  dword ptr [esp+4], 0xa
187  75 0d            jne  +0xd
189  8b 01            mov  eax, [ecx]
18b  8b 50 0c         mov  edx, [eax+0xc]
18e  6a 00            push 0
190  6a 05            push 5
192  ff d2            call edx
194  b0 01            mov  al, 1
196  c2 08 00         ret  8
```

It has its own prologue-equivalent, its own parameter (`[esp+4]`), its own virtual call and its own `ret 8`.
It is **not part of `0x0066ab70`** — the correct size is **384 (0x180)**, ending exactly after the 16-byte
jump table.

## Why it cannot be matched as scored

The candidate compiles to 384 bytes; the checker compares against a 409-byte span. To "match" we would have to
emit the neighbouring function's code inside our function, which is impossible — it belongs to another symbol.

## Action for the maintainers

Re-span `0x0066ab70` to **384 bytes**. Two other addresses have the same shape and were already excluded from
the worklists for it: `0x00bfb050` and `0x00ba5c50` (dead range, catch funclets).

## Action for an agent

Do not work it. This is the `index_problem` category, reported here rather than filed through `/api/v1/flag`
because the claim was released before a checkpoint id existed. If it is re-claimed, create a checkpoint and
flag with `category=index_problem, scope=unit, addresses=[0x0066ab70], checkpoint_id=<id>`.
