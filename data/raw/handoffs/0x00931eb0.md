### The `and esp,-16` red herring, settled
`__declspec(align(16))` *does* force `and esp,-16` at `/Od` — so the earlier report's reasoning
("aligned frame ⇒ /O2") was right by accident and the counter-argument in the brief
("aligned frame is not evidence of /O2") was also right. The shapes differ:

```
/Od : push ebx; mov ebx,esp; push ecx; and esp,-16; add esp,4; push ebp; mov ebp,esp; sub esp,0x30
      all locals and params in [ebp-N] slots
ORIG: push ebp; mov ebp,esp; and esp,-16; sub esp,0x54; push ebx/esi/edi
      temporaries at [esp+0x18]..[esp+0x5c]
```
What settles it is (a) the slot addressing (`/Od` never uses `[esp+N]` temporaries) and (b) the extent
test above. Do not use the prologue alone.

## What worked

1. **Read the type layout off the listing** and declare it directly (this is what the pack lacks —
   `symbol_note` says so). Confirmed offsets, all verified by the draft's own `/Fa` output:

```
Src (param1, ends in esi)          Dst (param2, ends in ebx)
 0x40 m_a   hkVector4               0x00 unk00 (void* = param1)
 0x50 m_b   hkVector4 (.w used)     0x10 CB2FC0Object m_xf[4]   (64 B each ⇒ 0x10..0x10f)
 0x60 m_q0  hkVector4               0x110 int m_count
 0x70 m_q1  hkVector4               0x120 CB2FC0Object m_work   (edi at entry = this+0x120)
 0x80 m_c   hkVector4 (.xyz used)   0x160 FUN_00cb21e0_shell (method called first)

```
`CB2FC0Object` is 4 × `hkVector4` (`m_r0..m_r3`) = 64 bytes; `m_r3` is the translation row and its
`.w` carries a per-element scale (1.08239996 = sec(pi/8) in the loop arm, `1/(1-angle²/2)` and
`1/(1-angle²/8)` in the two straight-line arms).

2. **Use the pack's own `hkVector4` inlines.** The skeleton already ships them (namespace
   `f3m_00925b30::f3m_00925b30`, note the double nesting) and the ORIG is built from exactly them:
   `setMul4` → `fld q0; fld r; fld st(0); fmulp st(2); …`, `addMul4` → same with `fld ST(0)` dup,
   `dot3`/`setCross`/`setAdd4` present too. `setMul4` + `addMul4` is what R3/R6 use.

3. **Name stand-in members `FUN_<addr>`.** `fc_check` derives the binding from the name (fc_check.py
   ~line 280–293), so `?FUN_00cb2d90@CB2FC0Object@@QAEXPAX@Z` binds to 0x00924b40 and a member called
   `FUN_008fda60` binds to 0x008fda60 **even though the shared symbol file has no entry there**. This is
   why the call in case 1 is expressible. Do not report a missing-symbol problem for 0x008fda60,
   0x00dfb608, 0x00dd8f60 or 0x00e37580 — pooled literals and unnamed code both bind this way.

## Two idioms that look like defects and are not

* **`fld x; fsubr st(0),st(0)` (DCE0) is not a negation idiom.** `fchs` is D9E0 and is what `-x` gives;
  DCE0 is what **`x - x`** compiles to (verified: `exp931/probe3.cpp`, `h1`). So the source really
  contains `p = (a->m_a(3) - a->m_a(3)) * a->m_b(3)`; MSVC cannot fold x87 arithmetic, so every
  consumer of `p` (= 0) and of `1-p` (= 1) is still emitted. That is why the function is 1891 bytes of
  work that is algebraically almost trivial. **Do not "clean this up"** — removing it changes the bytes.
* **`fsub qword ptr [__real@0000000000000000]`** is `x - 0.0f`: a float `0.0f` pools as a **double**.

## What did not work

* `setMul4` then `addMul4` as two statements gives one store per component with a reload between them;
  the ORIG **fuses** them. **Solved:** write the lerp as four explicit per-component sums —
  `out.m_quad[i] = (1.0f - p) * x.m_quad[i] + p * y.m_quad[i];` — which stores once per component with
  both weights held on the x87 stack, exactly the ORIG's shape (its 4th-component tail
  `fld/fmulp st(2)/fmul/faddp` then matches instruction for instruction). `cand_best.cpp` uses this and
  is better than the setMul4 draft (ndiff 613 vs 615 with the same extent). Residual: the ORIG loads
  `q0` before `q1` within a component and starts with an extra `fld st(0); fmulp st(2)` on `s`.
* Declaring `hkReal s = 1.0f - p;` gives `s` one slot; the ORIG has the temp in **two** slots
  (`[esp+0x1c]` computed, then copied to `[esp+0x28]` after the `FUN_00924b40` call), i.e. it is an
  inlined temporary, not a variable. Keep `1.0f - p` inline.
* Chasing the frame size and the param registers at 651/1891 bytes is wasted effort: the frame is
  `0x24` vs `0x54` only because R10–R22 are missing, and the register tie (`esi`=param1, `ebx`=param2,
  `edi`=`this+0x120` in the ORIG vs `esi`=param2, `edi`=param1 in the draft) should be re-examined
  once the whole body exists — §19.83 says ties follow the last offset that still matches.
