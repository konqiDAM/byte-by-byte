### R4 — case 0x26, detailed

**Corrected reading of the +0x0bb…+0x0dd block** (this one bit me, so it is spelled out):

```

```
So the "less" branch stores **0.0f** into `v`, not `F`.  The source is therefore

```c

if (F >= 0.0f) v = FUN_005843d0(blk, F);
else           v = 0.0f;
```
(VC8 re-uses the 0.0 that is already on the x87 stack for the comparison as the else value.)
Writing `v = 0.0f; if (F >= 0.0f) v = …;` is **not** the same for the compiler — it materialises the
0.0 into the slot up front and emits `fstp st(1)` / `test ah,5` instead of `fstp st(0)` /
`test ah,0x41`.  Use the `if/else` form above.

## 4b. RESOLVED: what the seven `FUN_00bee190` calls are

The level on the R8 path is constant (`L` = esp at +0x53d = **B-16**). Every `this` pointer of the
seven `FUN_00bee190(0xfa3, …)` calls is a **consecutive dword** `L+36, L+40, L+44, L+48, L+52, L+56,
L+60` = **B+0x14 … B+0x2C = `items[0] … items[6]`**, in that order, for bits 0..6 of `flags`:

```c
items[0]->FUN_00bee190(0xfa3, (float)( flags        & 1), 1);
items[1]->FUN_00bee190(0xfa3, (float)((flags >> 1)  & 1), 1);
items[2]->FUN_00bee190(0xfa3, (float)((flags >> 2)  & 1), 1);
items[3]->FUN_00bee190(0xfa3, (float)((flags >> 3)  & 1), 1);
items[4]->FUN_00bee190(0xfa3, (float)((flags >> 4)  & 1), 1);
items[5]->FUN_00bee190(0xfa3, (float)((flags >> 5)  & 1), 1);
items[6]->FUN_00bee190(0xfa3, (float)((flags >> 6)  & 1), 1);
```
(the int→float conversion is `mov [esp+0x10],reg ; fild dword ptr [esp+0x10] ; push 1 ; push ecx ;
fstp dword ptr [esp] ; push 0xfa3 ; call` — i.e. the compiler converts the *shifted int* to float and
pushes it as the float vararg).

## 4c. A reconstruction attempt exists and is close in size

`handoffs/0x0061bd10/best_cand.cpp` compiles, and its **frame size is already right**:
`sub esp, 0x148` + `__security_cookie` at B+0x144 match the original exactly.

(The first version of this candidate scored ndiff=502 / extent=1644; the two corrections in §4
— the `v = 0.0f` else-branch of R4 and the missing third branch of the R7 blocks — brought it to
1711 bytes of code, i.e. only ~104 bytes of the original are still not produced.  `ndiff` is a
coarse metric here: several semantically equivalent spellings of the R4/R7 float tests all land
between 495 and 506, so **read the assembly, not the number**.)

The four remaining `errs` are all "original relocation target differs", i.e. the checker compares the
relocation at the *same offset* in both, and my instruction there already differs — they are a
symptom, not an independent fault.

### What the diff already proves (measured, not guessed)

| | original | best_cand.cpp |
|---|---|---|
| frame | `sub esp,0x148`, cookie B+0x144 | **identical** |
| prologue | `push ebp; push esi; mov esi,[esp+0x158]; push edi; mov edi,[esp+0x158]` | `push ebx; push ebp; mov ebp,[esp+0x158]; push edi; mov edi,[esp+0x158]` |
| arg1 | `edi` | `edi` (same) |
| arg2 | `esi` | `ebp` |
| tagB | `ebp`, spilled B+0x00 | `ebx`, spilled B+0x0c |
| tagA | spilled B+0x10 | spilled B+0x10 (same) |
| items[7] | B+0x14..B+0x2f | B+0x24..B+0x3f |
| arg2 spill | B+0x30 | B+0x0c |
| buf2[0x10] | B+0x34 | B+0x14 |
| buf1[0x100] | B+0x44 | B+0x44 (same) |

So the **frame size and the two ends of the layout are right**; the middle (which local gets which
slot) and the register colouring (esi vs ebp vs ebx) are not.  This is the "position and colouring
are coupled" case from `NIGHT_BRIEF_COMMON.md` §2 — fixing the slot order will move the registers
and vice versa, so treat them as **one** problem, not two.

### Experiments already run (do not repeat them)

* **Negative result (measured): the order of the local declarations does NOT move the frame slots.**
  Three variants were compiled — swapping `buf2`/`items`, moving `int flags` to the top of the
  function, and swapping the two float locals `v`/`F`.  All three produced **byte-identical output**
  (ndiff 502, extent 1644, same prologue).  So VC8 is not laying the locals out in declaration
  order here; the slot order comes from the allocator's own ordering of the live ranges.
  Do not spend time on declaration-order sweeps — the lever has to be the *structure* of the source
  (which value is live across which call), not the order of the declarations.
  (The variants are in `work/61bd10/v_A_swap_buf2_items.cpp`, `v_B_flags_first.cpp`,
  `v_C_swap_vF.cpp`.)
* Declaring `tagB` **before** `tagA` → the compiler then calls `FUN_00bea9e0(DAT_00e035d8)` **first**;
  the original calls with `DAT_00e035e0` first.  The source order must therefore be
  `tagA = FUN_00bea9e0(DAT_00e035e0)` **then** `tagB = FUN_00bea9e0(DAT_00e035d8)`, and the
  allocator puts `tagB` at the *lower* slot (B+0) because it is the longer-lived value.
  (`work/61bd10/cand4.cpp` is that experiment; it is worse: ndiff 510.)
* `extern const char* A, B, C;` declares **only A** as a pointer — `B` and `C` become
  `const char`.  The six `DAT_00f635xx` globals must each have their own `extern const char*` line.
  (Cost me 10 minutes; the compiler error says "Conversion from integral type to pointer type".)
* `(long)floatExpr` → `call __ftol2_sse` with the float in st0: **verified** by a probe compile
  (`work/61bd10/t1.cpp`).  Never hand-declare `__ftol2_sse`.
* `float f; f / 100.0` → `fld f; fld QWORD PTR __real@4059000000000000; fdiv ST(1), ST(0)`
  — the same shape as the original at +0x29f, and the constant binds to **0x00dba730** correctly.

### What to try next, in order

1. **Slot order — via source structure, not declaration order** (declaration order is proved not to
   matter).  The original's layout is
   `tagB, v, arg1(spill), F, tagA, items[7], arg2(spill), buf2[0x10], buf1[0x100]`.
   In the original, `v` and `F` are *spilled floats* (B+4 and B+0xC) because they are live across
   calls; in `best_cand.cpp` they never reach the stack at all.  So the lever is: make `v` and `F`
   values that are still needed **after** the calls inside their case block (in the original, `v`
   is used by `FUN_0047ca30` and `F` by `FUN_0090d870` *after* `FUN_005843d0` has been called),
   and make `arg2` die after the gather loop so its spill lands at B+0x30 rather than B+0x0c.
2. **Register colouring.**  The original wants `arg1→edi, arg2→esi, tagB→ebp, flags→ebx`.
   `flags` is the value that lives in ebx and is *pushed late* (+0x089) in the original; if your
   build puts `tagB` in ebx, `flags` will end up elsewhere.  Making `flags` a single variable that
   is only written in the switch and only read in R8 is what lets VC8 give it ebx and push it late.
3. Then re-run `asm3.py` — the first difference is the prologue, so the slot order and the
   register order have to be fixed **together** before anything downstream can line up.

## 5. Open questions (ranked)
1. **The `switch` shape.** The original compares 0x18, then 0x1a, then 0x26 (`sub eax,0x18 / je / sub eax,2 / je / sub eax,0xe / je`) but lays the **0x26 body first** (+0x0a8) and the 0x18/0x1a body second (+0x296). Try a `switch` and an if/else chain and see which reproduces that layout.
2. **R4/R5 float condition polarity.** `test ah,0x41` + `jp` = "not less"; decide per site whether
   the source condition is `<`, `>=`, `>`, or `<=`. The compiler will tell you: write the natural
   C++ and compare the branch polarity in the diff.
3. **Whether `FUN_0047ca30(v, 1.0f)` is really `FUN_0047ca30(v, 1.0f)`** — the callee computes
   `b/b` internally (see `0x0047ca30`), so it returns `a` unchanged; but the *call site* must push
   1.0f as the second argument.
4. **`FUN_00456720(blk)` is called twice** with the same argument and the second result is used
   (`esi`). Write it as the source did (a call the compiler could not CSE — probably because the
   callee is not `const`/pure), e.g. `k = f(blk) ? f(blk) : 1;`.
5. **The `0x100`-sized `FUN_00403cf0(buf1, 0x100)`** and the inlined `strlen` — `buf1` must be
   declared `char[0x100]`.
6. The `switch` must be written so VC8 emits the *sequential-compare* form and lays the 0x26 body
   out first — try both a `switch` and an if/else chain; the diff will show which matches.
7. **The 8-byte compare at +0x53d** (`mov esi,[DAT_0106cb94]` / `mov edi,0x00db9364` /
   `repe cmpsb` with `ecx=8`) compares against the **literal at address 0x00db9364**. A string
   literal in your source lands at a different address and the immediate would not match; the
   literal has to come from the same rdata object (the pack does not export it — check whether the
   checker can bind it by name).
8. **`items[3]` is used both as a `this` pointer and as the `const char*` text** of the six
   `FUN_00bf11a0` calls — `items[]` cannot be one homogeneous type; find the declaration that
   makes both uses legal.
