Both forms test the same bit: **bit 1 of the byte at item+0x25** (= bit 9 of the dword at
item+0x24). The rival draft expresses it as a 32-bit bitfield
(`struct Hi24 { unsigned int lo:9; unsigned int high:23; };` then
`(unsigned char)((Hi24*)((char*)item+0x24))->high & 1`), which is why the compiler loads a
**dword** and shifts by **9**. The original loads the **byte at +0x25** and shifts by **1**,
then tests `dl,1`.

Length note: both blocks are 8 bytes, so the extent stays exactly 2344. The whole rest of the
function (2336 bytes) matches byte-for-byte; the block is in the `&unk604` SaveLink walk loop
(the one that writes only items whose flag bit is clear).

## What was tried (all offline, score_pack; 40+ spellings)

All of these **fold** into `test byte ptr [eax+0x25], 2` (3 bytes shorter), which then rotates
the whole loop's register web (ebx/ebp swap, counter slot moves) and explodes to ndiff 127:

* plain `!((*(unsigned char*)((char*)item+0x25) >> 1) & 1)` and 20 spellings of it
  (`%2`, `&1u`, `!=0`, `==0`, `==1`, `!!`, mask-then-shift, shift-then-mask, `/2`, `1 &`,
  `(unsigned char)` casts at every position, `bool` cast).
* byte-sized **bitfield** structs at +0x25: `{a:1;f:2;r:5}`, `{a:1;f:7}`, `{f:8}`, `{f:2}`,
  `{p:1;f:2;r:5}`, and `{p:1;f:2;r:5}` on a `unsigned short` at 0x24 — all fold.
* named locals holding the byte / the shifted byte / the masked bit (`unsigned char`,
  `unsigned int`, `int`, `bool`), both statement-split and single-expression — all fold.
* `volatile` byte read: blocks the fold but costs a stack slot and moves the counter from
  `[esp+0x3c]` to `[esp+0x18]` (ndiff 20/77), and volatile does NOT produce the byte load.
* 32-bit value + mask + shift chains that narrow to the byte (`(v & 0xff00) >> 9`,
  `(unsigned char)(v>>8) >> 1`) — MSVC merges the shifts (`shr 9`) and folds the mask.
* `% 2` on the shifted byte **does** produce the wanted `movzx edx, byte[eax+0x25]; shr edx,1`
  but appends the signed-remainder fixup `and edx,0x80000001; jns; dec; or; inc` (ndiff 22).

## Conclusion / next hypothesis

This is very likely a **backend tie-break on one load width** (brief §3.1 category
"compiler tie-break"): the structure, extent, bit, branch and every other instruction are
exact. VC9 folds `(x >> 1) & 1` on a byte lvalue into a memory bit test in every source shape
tested; the original kept the shift, so its source must have materialised the shifted value for
another reason. Remaining ideas for a longer search (none tested to completion):

1. the shifted value is used a **second time** in the original (a use that the draft's other
   constructs already cover) — test with a shape where `word = item->unk25 >> 1` feeds both the
   bit test and another store/branch;
2. an original source where the byte at 0x25 is read through an inlined `unsigned char`
   accessor whose value also feeds a `SaveScalar`/stream write (the draft writes `item` only);
3. accept it on the build host: the released code is ndiff 2 / extent exact, the solver's
   longer search has finished near-misses like this before.
