# 0x00a560b0 — CheckTransformAndProcess: the pack's RETURN TYPE is wrong (short, not int)

**Status: released `symbol_problem`** (claim `clm_2117a745a66f43aa99c5`, 161 B, 5 reports, 36 give-ups).
This one is genuinely blocked, and here is the proof.

## The pack wants an `int`-returning symbol

```
?CheckTransformAndProcess@@YAHPAXPAUObjOuter@@0PAF@Z    ->  int __cdecl (void*, ObjOuter*, ObjOuter*, float*)
```

## The original returns 16 bits, twice

```
+0x055  je 0x61
+0x057  66 33 c0        xor   ax, ax          <- return 0
...
+0x095  66 8b 44 24 1c  mov   ax, [esp+0x1c]  <- return (short)iResult
+0x09a  pop edi / esi / ebx / mov esp,ebp / pop ebp / ret
```

Measured with `exp91\codegen_probe.py` (VS2005 SP1, /MT /O2 /GS /EHsc /Gy):

| source | bytes |
|---|---|
| `short f(void) { return 0; }` | `66 33 c0 c3` = **xor ax,ax; ret** |
| `int f(void) { return 0; }` | `33 c0 c3` = xor eax,eax; ret |
| `short f(int v) { short s = (short)v; return s; }` | `66 8b 44 24 04 c3` = **mov ax,[esp+4]; ret** |
| `int f(int v) { short s = (short)v; return s; }` | `0f bf 44 24 04 c3` = movsx eax,... |

Only a **16-bit return type** produces those two instructions. An `int` return always widens
(`movsx eax, word ptr [...]`) and `return 0` always clears all of eax. There is no source shape
that gives `mov ax` for an `int`-returning function, so the symbol `...YAH...` can never be
matched. The correct mangled name would start `?CheckTransformAndProcess@@YAFPAXPAUObjOuter@@0PAF@Z`
(`F` = short).

Also wrong in the pack, same class of defect: the unit's own declaration at line 358 is
`int __cdecl CheckTransformAndProcess(void* p1, ObjOuter* pOuter, void* p3, short* outWord)` —
param 3 is `void*` there (`PAX`), while `pack.json` requires `ObjOuter*` (`0`). Two different
manglings for the same function.

## The body (for whoever gets the symbol fixed)

The twin (`src/havok/physics/collide/util/welding/hkpmeshweldingutility.cpp:439`, FNV
`0x00dde880`) is the right structure. What the F3 bytes add to it:

* `pOuter->GetInner()` (vtable slot 5 = `[vtable+0x14]`), then `inner->GetTransform(p1, &buffer)`
  (also slot 5). Both are the unit's `ObjOuter`/`ObjInner` (unit lines 334-350).
* `IsDegenerateTriangle(&checkResult, &trans->v0, &trans->v1, &trans->v2, 1e-7f)` with
  `Transform { int pad[8]; FourFloatVector v0, v1, v2; }` -> +0x20/+0x30/+0x40, epsilon from
  `flt_01065384`. The char result is dereferenced: `if (*IsDegenerateTriangle(...)) return 0;`
  (the F3 build returns 0 here, the FNV twin returns 1).
* Loop `for (i = 0; i < 3; ++i)` over a **7-argument** callee at `0x00a55e90` — one more argument
  than the unit's 6-arg `FUN_00dde4c0`: the pushes are
  `p3, &iResult, i, p1, trans, pOuter, &checkResult` -> `f(&checkResult, pOuter, trans, p1, i,
  &iResult, p3)` with `add esp,0x1c`. The loop ignores the return value (no `if (iRet == 1)`
  accumulator in this build).
* `return (short)iResult;`, and the 4th argument is never touched.
* Frame `push ebp; mov ebp,esp; and esp,-16; sub esp,0x214; push ebx/esi/edi` = 16-byte aligned
  `LocalBuffer` of 500 bytes at `[esp+0x20]`, `iResult` at `[esp+0x1c]`, `checkResult` at
  `[esp+0x2f]` (the compiler packed the char inside the aligned array's slack — do not try to
  force that, let the compiler decide).
