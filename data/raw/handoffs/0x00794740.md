## Third burst — new best `63 / 511` (the `bool live` discovery)

`out\0x00794740\best.cpp` is now the variant that names the `v100()` result before the `&&` chain:

```cpp
        F3XEntry* entry = ((F3XEntry**)unk08)[i];
        F3XOwner* owner = entry ? entry->m_pkOwner : 0;
        bool live = entry->v100();
        if (live && owner && owner->v574())
            owner->v57C(entry);
```

`ndiff 63, extent 511 vs 518, errs 4` (was 78 / 511). Why it helps: in the `&&` chain the call
result stays live in a register across the two later virtual calls; naming it lets cl keep it in
`al` instead, which frees a register and moves the **owner** web to `edi` — exactly the original's
pick. Owner now matches; the walk below is byte-for-byte instructions.

Remaining, and it is now only two register names plus seven bytes:

| where | ORIG | ours |
|---|---|---|
| notify loop index | `esi` | `ebx` |
| notify loop entry | `ebp` | `esi` |
| `0x002b` loop entry test | `mov esi,[ecx+0x14]` / `mov eax,[ecx+0x24]` / `cmp esi,eax` | `mov ebx,[ecx+0x14]` / `cmp ebx,[ecx+0x24]` (3 B shorter) |
| `0x00a0` head | `test ebp,ebp` + `je` (4 B) | absent |

Measured around the new best: `live` as `!= 0` (`65 / 516`), `!!` (`65 / 516`), `if (live) { if
(owner && ...) }` (`63 / 511`), `continue`-per-condition (`63 / 511`), `owner && live &&` reorder

Interpretation: the index web in the original coalesces into the walk's `item` web (`esi`) and the
entry web into the walk's `node` web (`ebp`); ours coalesces index→`ebx` (which the walk later uses
for the list head) and entry→`esi`. That is the register allocator's scan order over the whole
function, and it is the same rotation that drops the 4-byte head test — all three residues are one
function-level allocation decision, not three independent bugs.

Next ideas, in order: (1) get the notify loop's entry web to coalesce with the walk's node web — e.g.
by making them the same source value (an `entry` that is *stored back* into a variable reused by the
walk is not possible, but a single `node` variable used by both parts is worth one test); (2) the
`0x002b` double load is the `for` entry test, and only appears when the back-edge test re-reads the
member, which the `end`-in-a-local shape destroys — so it must come with the register fix, not from
an `end` local.

Why the head-hoist theory is dead: hoisting makes it *worse* by 12 bytes, because the original
rematerialises the head at `0x88` (`mov ebx,[esp+0x18]; add ebx,0x58`) instead of keeping it in a

index out of `ebx`.

State of the coalescing question: the index stays in `ebx` in every shape measured (10 here, 60+
overall), while the original has it in `esi` with the entry in `ebp`. Both functions coalesce
vertically in the same way (index→item / entry→node in the original; index→head / entry→item here),
so the difference is purely the allocator's register *choice* for the three notify-loop webs, not a
live-range or coalescing difference I can reach from source. `int live` did lift one instruction to
match (the loop's `jae` becomes the near form the original uses), which is the 3 bytes of extent and
3 diffs of score.
