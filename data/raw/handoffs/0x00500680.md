## Why it is not a symbol defect

The three data addresses (`0x00dcfb0c`, `0x00dcfaf8`, `0x00dcfa74`) are **not** in the shared
symbols file. That is survivable: declare them yourself (`extern char DAT_00dcfb0c[];` and store
`(void*)DAT_00dcfb0c`) — the binding is then derived from the original bytes and the literal check
skips an undefined external. So this is difficulty, not a defect:

* the store `[esi+0x18]` is written twice with two different tables -> the class has a **virtual
  base** (base ctor sets the base table, the most-derived ctor overwrites it), and the layout of
  that vbase decides the whole frame;
* the member at `0x2c` is built by a 5-argument ctor `(this+0x2c, 0xc, 4, fn, fn)` — the `0xc`
  is an element size, so it is an array-like member;
* two EH states, so two sub-objects with destructors.

That is a lot of layout guessing for a 166-byte function and I ran out of budget. The order of the
statements, the calls and the offsets above are exact; start from them.
