## Why the earlier diagnosis was wrong

The packet/claim note said the residue was "a symbol bug: the draft defines DAT_0107c054 instead of declaring it".
It is not. The draft declares it `extern` and the object really has an *undefined* symbol
(`?DAT_0107c054@@3PAUS78ed50_Ref@@A`, section 0). The four relocation errors are a **downstream artifact**:

- `f3check\fc_check.py:derive_bindings` binds a name that has no canonical binding from the **first** relocation site.
- In the draft the first site is `+0x4d`, but at `+0x4d` the *original* holds the tail of `mov edx,[eax+0xfc]`
  (`8b 90 fc 00 00 00` read at `+0x4d` = `0x00fc908b`), so the derived address is garbage and every later site mismatches.
- The real difference at `+0x4b` is 3 instructions' order:

```
original:  mov eax,[ecx] / mov edx,[eax+0xfc] / mov dword ptr [DAT_0107c054],ebx / call edx
draft   :  mov dword ptr [DAT_0107c054],ebx / mov eax,[ecx] / mov edx,[eax+0xfc] / call edx
```

That is exactly the give-up reason already recorded in the packet history ("R1 0x4b-0x53 only ... R2-R6 exact").

## Why `static` is the fix (and why it is plausible as the true source)

The store can only be emitted *after* the two vtable loads if the compiler can prove `[ecx]`/`[eax+0xfc]` cannot
alias `DAT_0107c054` — with `extern` the address may have escaped to other TUs, so MSVC keeps the store first.
With internal linkage and no `&DAT_0107c054` in the TU, MSVC proves no alias and sinks the store into the slot
before the call: byte-identical, no other byte changes anywhere in the 1399.

Corroboration that the variable is really TU-local: the immediate `0x0107c054` appears **nowhere else** in
`Fallout3.exe` except inside this function and its neighbour `0x0078f2d0` (39 sites, all in
`0x78eda5..0x78f2df`). A cross-TU global would show up in other functions.

Caveat for the main session to weigh: if the original *did* have external linkage, this declaration is a
scheduler lever rather than a faithful declaration (relocation-by-name still resolves to `0x0107c054`, so the
checker cannot tell). Everything else in the function matches, and the residue cannot be reproduced with any
external-linkage form.
