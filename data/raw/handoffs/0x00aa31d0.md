## 2026-11-13T13:55Z - the ecx mechanism is found; why it still cannot be combined (read before re-sweeping)

Best unchanged: `out\0x00aa31d0\best_nd3.cpp`, nd 3 bytes / 3 insn, extent 449, errs 0. Nothing submitted.

### ecx at 0x10e is a *member `this` temp*, not a colour choice (measured)
`dead.set(next); dead.clear2(); unsigned old=candidate.bits; long r=dead;` (v25\d1.cpp) gives
`010e mov ecx,[esp+0x14]` - the ORIG register exactly. Inside the inlined body the folded `this`
address takes the first scratch slot (eax) and the load takes the next (ecx). Cost: the and and the
store then follow the load directly (0x112/0x115) and the volatile candidate read is pushed to 0x119
-> 32 bytes. Same source with a named temp (v25 e2/e3/e6) -> eax. So ecx <-> unnamed scratch in one
statement, with a `this` temp in front.

### Why the ORIG order cannot be added to that (measured, ~40 new variants)
With load+and+store in one statement, a volatile read in the same statement is **hoisted to the
statement front** (`dead.Ref()&(old=candidate.bits,~1u)`, `x-(old=c,0u)`, `x>>(old=c,0u)`,
`(dv=dead.Ref(),old=c,dv&~1u)` - all emit the candidate load first, 26 bytes). Only a **comma chain**
keeps source order (v30\k1: `dead.bits=(dv=dead.bits,old=candidate.bits,dv&~1u)` -> order exact,
nd 3) and a comma chain forces the value into a **named local**, which is coloured -> eax.

Deduction from the listing: in ORIG the load (0x10e) and the store (0x119) are NOT adjacent, so they
are not one statement (a load and its store move together - compiler_tips.md). The value therefore
crosses a statement boundary, which in C++ means a named local, and a named local in this block takes
eax (measured 8 ways). The two requirements are mutually exclusive here.
