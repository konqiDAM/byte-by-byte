Two facts that are worth keeping:

1. **`if (!n->item) return;` keeps the loop cursor in `eax`.** Spelling the null test on the local

2. The base needs **two** variables: one memory-resident (address taken) and one promoted to `esi`
   (used across the call for `push esi`). That shape is what makes the compiler use two callee-saved

## What worked (mechanisms, not spelling)

1. **The helper imprisons the store.** A store written inside a `__forceinline` helper (`home = v`
   through a reference param) is emitted at the helper's inlined position and CANNOT sink into the
   match block — while an identical caller-side store (`key = item` in a `&&`/ternary arm or in the
   if-body) **sinks to the escape point inside the match block** (measured, d3: `cmp; je` direct,
   store gone from the window). This is why fB2's store sits between the cmp and the branch and d3's
   does not. Caller-side arm stores are dead as a class.
2. **fB2 family reproduced the promoted store.** Helper
   `bool Take(Entry*& home, Entry* v, int id) { bool r = v->id == id; home = v; return r; }`
   called as `if (Take(key, item, id))` with `item = n->item; Entry* key;` (key assigned ONLY via
   the helper) gives — for the first time in any shape —
   `push edi / mov edi,[esp+8] / mov esi,[eax] / test / je / cmp [esi+0x30],edi / mov [esp+0xc],esi / sete dl / test dl,dl / jne L_match-far`.
   The handoff's hypothesis-1 store (home written from the promoted register, after the compare) is
   **reachable from source**. Extent 76, ndiff 11, errs 1.
3. **fB3 family** (`{ home = v; return v->id == id; }`): store from esi before the cmp, cmp through
   esi, **direct `je` to the far match block (no sete!)** — but `id` drops to `edx` and push/pop edi
   are lost (extent 68). Proves the direct-branch form exists; its statement order is wrong.

## The two walls that now replace the old bracket (both measured, both one-mechanism wide)

**Wall A — the sete.** MSVC materializes the helper's bool return (`sete dl; test dl,dl`, +5 B)
whenever the comparison is not the helper's LAST statement. Store or dtor between the cmp and the
`return` ⇒ materialization (fB2, d1/d2/d9 all identical). cmp-last ⇒ flags branch directly (fB3).
So "store after the cmp inside the helper" and "branch directly on the cmp" are currently mutually
exclusive *inside one helper*. Note: in d1 (dtor) the flags physically SURVIVE the store — `sete dl`
at 0x1f still reads the cmp's ZF set at 0x18 after the store at 0x1b — the compiler merely chose to
materialize. Whatever convinces the middle end to keep the return value in flags across one
statement inside the helper closes Wall A and lands extent 73−2+0 = 71 → then only Wall B remains.

**Wall B — the load/copy split.** ORIG loads into `edx` and copies `mov esi,edx` after the null
branch; every helper shape loads straight into `esi` (one SSA value: the load feeds test, item and
the param temp; the coalescer merges them). The probe/item split (`Entry* probe = n->item; …
Entry* item = probe;`), pushing `probe` across the call (s8), and cast/pointer chains do NOT split
it — the coalescer wins (s1–s8 all extent 76/11 like fB2). Two SSA values so far require the
address-taken `key` to be assigned early = the old early-store wall. Untested: pass the value as a
by-value struct member (`struct W { Entry* p; }; W w; w.p = n->item; Take(key, w.p, id)`),
`Entry* const&` temp binding, or whatever makes MSVC 2005 refuse v←item coalescing.

Also measured dead tonight: compare-as-forwarder is fully transparent (fA = baseline bytes); id-first
or home-last helper param orders lose `push edi` (d7/d8) — the `(home, v, id)` order is what keeps
`id` in `edi`; scope-hoisted item/key (outside the loop) explode to extent 84–99 (h1–h3); dual-arm
ternary stores do not hoist/CSE (t1–t4, extent 68/86); fold-away binary carriers
`(cmp) & (store,true)` / `(cmp) + (store,0)` (w1–w6) materialize the cmp for the operator (setcc,
extent 81) — the operator consumes the value, so the store cannot ride behind the cmp this way.
