## Verdict (read this first)

**The 20-byte span at 0x00c1059e is arm #23 of a 64-entry jump table.** It is not a function,
has no prologue, and consumes x87 registers (`st(0)`, `st(1)`) that are live on entry. No C++
source can produce it as a standalone function, so the 18 give-ups on this address have a cause
and are not a model failure. `symbol_problem` is the right report; a second flag adds nothing (one
is already `awaiting_triage`).

Evidence in one line each:

1. 0x00c1059e is **entry 23 of 64** of the dword table at `0x0106ba8e` in `.data`
   (file offset 0xc69cea = VA 0x0106baea = `0x0106ba8e + 23*4`).
2. That table has exactly **one** reference in the whole image: `jmp dword ptr [eax*4 + 0x0106ba8e]`
   at `0x00c1044d`, reached from `sub esp,0x2c` / `and eax,0x3f` at `0x00c10447` / `0x00c1044a`.
3. **Every** one of the 48 index entries in 0x00c10454..0x00c108d2 is a target of that table
   (48 of the table's 64 entries; the other 16 are not indexed). The whole cluster is one blob's
   switch arms.
4. `0x00c1059e` occurs **once** in the entire 15,044,024-byte image: as that table entry. No
   `call`/`jmp` rel32 in `.text` targets it (exhaustive scan of every `e8`/`e9` in `.text`).
5. The arm's `add esp,0x2c` matches the **single** `sub esp,0x2c` in the dispatch block at

6. Neighbouring arms reference `st(1)` … `st(7)` (`fxch st(6)` at 0x00c108a9/0x00c108be), so the

### Reachability of the dispatch block

Exhaustive scans, all negative:

- no `e8`/`e9` rel32 anywhere in `.text` targets 0x00c10447 or any of the 64 arms;
- no 4-byte value `0x00c10447` anywhere in the file (so no `push`/`mov`/indirect-call table
  points at it either);
- the single reference to the arm address 0x00c1059e is the jump-table slot;
- the code immediately before 0x00c10447 is `fdivp st(1); ret` at 0x00c10444-0x00c10446, so there
  is no fall-through path;
- the only `jcc`/short-`jmp` within ±127 bytes jump to 0x00c10338 / 0x00c103d4 / 0x00c10418 /
  0x00c10420 / 0x00c10440 — none into the blob.

So the blob 0x00c10447..0x00c108e5 is **unreferenced (dead) CRT code**. Conclusion: even the
"correct" span is not a callable function; it is one unreachable asm blob, and the index has
carved it into 48 pseudo-functions.
