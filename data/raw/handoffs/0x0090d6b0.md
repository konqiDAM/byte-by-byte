## Progress

The draft is byte-exact over the whole function (extent 159 = target, 0 errs). **One 2-byte
region differs**: the position of `push ecx` relative to the final `fstp`.

```
0000-0071  identical
006f  fld  dword ptr [ecx+0xc]      ; rotation.w
0072  lea  ecx, [esp+4]             ; &cmd
0076  push ecx                      ; <- ORIG
0077  fstp dword ptr [eax+0xc]      ; <- ORIG   (ours: fstp at 0076, push at 0079)
007a  mov  ecx, dword ptr [esi+8]
007d  call FUN_00902570
```

Same instruction multiset, same total length, one slot swapped. Nothing else in the function
differs, so this is pure scheduling, not shape.

## What did not work (all measured, ~620 distinct source shapes)

Combinations that all give **exactly ndiff 4 bytes = the same swap** (400 of 500 in the big sweep):
- copy form: `data[0]=p; data[1]=r` / `*(data+1)=r` / `Vec4& dst=data[1]; dst=r` /
  `data[1].Copy(r)` / lane-by-lane with the w lane named / reference to the element /
  `((Vec4*)data)[1]=r` / `data[1].operator=(r)`
- argument form: `&cmd` / `Cmd* p=&cmd` / `Cmd& r=cmd; &r` / `Cmd* const pc=&cmd` /
  `(void)call(...)` / comma expression / `&cmd` through an `__forceinline` forwarder
- zero-cost aliases (lever L3): `const Vec4& p0=position`, `r1=rotation`, both, `World* const w0`,
  `Cmd& pc = cmd` — all neutral (code identical), so P is not the knob here
- guard shape: `if(world&&world->active){...return;}` vs inverted guard — source order of the two
  led stores *does* matter (`cmd.owner` before `cmd.type` costs 12 bytes), but nothing moves the push
- copy order swapped in source (`data[1]` first) — emitted order is unchanged, so the scheduler
  reorders the copies anyway; source order is not the tie-break here
- callee body visible (`__declspec(noinline)` definition) → 151 diffs (worse)
- `Vec4` return-by-value helper (`cmd.data[1] = MakeVec(rotation)`) → 185 diffs
- `volatile` float store on the last lane (addendum trick) → 152 diffs; it pins the store *before*
  the push, i.e. the wrong side
- `if (0) vp = &rotation;` dead-code address-take → neutral (4)
- naming the payload pointer (`Vec4* d = cmd.data`) → 67 diffs (it stays in a callee-saved reg)
- `void*` payload field + casts, `unsigned long key = DAT_010f3170;` local, `sizeof` args,
  union buffer for `cmd`, `Cmd cmd` declared later → all worse (27–196 diffs)
- full L8 permutation proof of the four memory stores (type / owner / data[0] / data[1],
  all 24 orders, twice): only the canonical `type, owner` before the allocator and the two
  copies in order reaches ndiff 4; every other order is 36–90
- the twin's own idiom (`world->FUN_00902570(&cmd.Fill(a,b))`, member returning `*this`):
  tested **directly on 0x0090d6b0** in round 12 (no receiver local, cast inline) → still 4 bytes,
  same residue; a void member writing through `this->data` likewise
- flag matrix on the standalone draft (pack flags vs `/GS-`, `/Ob0`, `/Ob1`, `/Ob2`, `/Oy-`,
  `/Oi-`, `/Os`, `/Ot`, `/Ox`, `/O1`, `/G6`, `/G7`, `/Ox /Oy-`): no set emits push before the
  fstp, and only the pack set keeps 159 bytes — so this is not a flag artifact
- `Cmd* pc = &cmd` taken *early* in the block (an earlier symbol number for the argument value,
  the scheduler's tie-break) and `Cmd cmds[1]` / `&cmds[0]`: all still 4 bytes

## Hypotheses / next steps

Class **2**: eax/ecx availability. The mechanism we can see: `lea ecx,[esp+4]` must precede
`push ecx` (push writes esp), and `mov ecx,[esi+8]` forces ecx free right after the push, so
ORIG emits `lea;push` as a unit and lets the pending x87 store flush after it. Our drafts give the
pending store priority. Ideas that were *not* tried:
1. Make the value in `eax` at the residue depend on something later (the brief's own lever for
   class 2: "change what produces the value occupying eax"). Reducing the second copy's base to a
   reload after the push was not achievable without changing bytes.
2. `#pragma` warning/intrinsic level changes are refused; a real re-read of `cmd.data` between the
   copies (`(void)cmd.data;`) was not tried.
3. Try RTM/vc8 or an `accept_also` flag set — the brief notes SP1 sometimes cannot produce a
   register/order choice and RTM can (pack lists only `/MT /O2 /GS /EHsc /Gy`; no `accept_also`).
4. The build host solver is the realistic closer: this is a 4-byte permutation of two adjacent
   instructions, which is exactly what a permuter search is good at.

**0x0090d750 shares the fix**: yes — whatever moves the push ahead of the final `fstp` in
0x0090d6b0 will almost certainly close 0x0090d750 too (same offset 0x76/0x77, same idiom, same
`FUN_00902570(&cmd)` + `DAT_00d9b080(TlsGetValue)/FUN_008f6d30` allocator prologue). No source
shape found in ~620 tries moves it, so this is likely one shared answer or one shared wall.
