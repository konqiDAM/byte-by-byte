## Why (measured, not guessed)

1. The pack compiles with `/Gy`, and VC9 puts **every function in its own COMDAT section**
   (`exp91/codegen_probe.py` on a two-function file prints two `.text` sections of 10 bytes each).
   So `coff.sections[symbol['section']]` for FUN_009035e0 holds only FUN_009035e0.
2. `f3check/compare.py:181-189` bounds the compared extent at the next symbol of type
   `IMAGE_SYM_DTYPE_FUNCTION` **in the same section**, else at the section end.  Two functions can
   therefore never be inside one symbol's extent under `/Gy`; without `/Gy` the *next function
   symbol* still ends it (`end = min(next_entries)`), so the answer is the same.
3. Section/segment control is not available: `fc_check.DIRECTIVE` drops **every** preprocessor
   line except `#include <crt/std headers>` and `#pragma intrinsic/function`, so `#pragma code_seg`
   or `#pragma comment(linker,...)` never reaches the compiler.
4. A *single* C++ function cannot produce this span either: byte +0x4f is a plain `ret` (`c3`) and
   byte +0x99 is `ret 8` (`c2 08 00`).  VC9 emits the same epilogue for **all** returns of a
   function (either `ret` when it has no stack parameters or `ret N` for all of them), so no source
   gives `c3` at +0x4f and `c2 08 00` at +0x99 in one function.  `naked`/`__asm` are refused by
   the checker, and a switch table would have to be relocations, not those instruction bytes.

**Conclusion: any index entry whose canonical span contains two (or more) real functions is
unmatchable until the index gains an entry at the second function's start.**  For 0x009035e0 the
fix is one entry: **0x00903630, size 76**.  Nothing about the C++ changes that; it is the checker's
extent rule meeting `/Gy`.

## What the four callees show (useful for whoever gets the split entries)

Disassembling the callees proves the caller's `mov esi, ...` / `mov esi, edi` are **argument moves for a
private (compiler-chosen) convention**, not dead locals:

* `0x009033c0` reads its argument from **esi** and takes nothing on the stack (`mov [esi+0x40],al`).
* `0x00903550` reads arg1 from the stack (`[esp+0xc]` after 2 pushes) and `this` from **edi**.
* `0x00903460` reads `this` from **esi** (`[esi+0x28]`) + one stack arg.
* `0x009034c0` takes both args on the stack (normal `__cdecl`), `this`=arg1 in ebp.

So the original TU had these as `static` functions and `/O2` gave each its own register convention
(`compiler_tips.md` "Inputs in registers"). To reproduce, the callee **bodies** must be in the same TU
as `static __declspec(noinline)`; an `extern` declaration can never produce those register moves.
Measured: bodies that keep the pointer live across a call make the caller hold the object in `esi`
(a probe compiled `push esi; mov esi,[arg]; call`), i.e. the shape is reachable, but the extra
`mov eax`/param-colouring per callee needs its own search - and it is wasted until the span is split.
