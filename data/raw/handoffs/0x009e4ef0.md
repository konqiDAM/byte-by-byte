## The one residue that was open, and the fix
The previous draft was 2 bytes off (everything else matched):

```
ORIG  fld dword ptr [ebx + 0x30] / fadd dword ptr [ebx + 0x40]     (box.max[0])
OURS  fld dword ptr [ebx + 0x40] / fadd dword ptr [ebx + 0x30]
```

`box.max[0] = m_halfExtent[0] + m_center[0];` (and swapping the operands in the source) does
**not** help: MSVC /O2 canonicalises a commutative add of two members of the same object and
always emits `fld <higher offset>` / `fadd <lower offset>` — verified with micro-probes
(`claims/clm_c2d18266368d48c19ea4/probe*.cpp`). Source order, extra parentheses, temps,
`+=`, `+=` on the destination, inline helpers, `float`/`const`/`volatile` variants and loop
forms all produce the same canonical order.

**The fix**: give `m_center[0]` a *prior use* in the function, by splitting the index-0 `min`
through a temp:

```cpp
    float c0 = m_center[0];
    box.min[0] = c0 - m_halfExtent[0];
    box.min[1] = m_center[1] - m_halfExtent[1];
    box.min[2] = m_center[2] - m_halfExtent[2];
    box.min[3] = m_center[3] - m_halfExtent[3];
    box.max[0] = m_halfExtent[0] + m_center[0];
    box.max[1] = m_halfExtent[1] + m_center[1];
    box.max[2] = m_halfExtent[2] + m_center[2];
    box.max[3] = m_halfExtent[3] + m_center[3];
```

The `min[0]` bytes are unchanged (`fld [ebx+0x40]` / `fsub [ebx+0x30]`), but the add of
`box.max[0]` is no longer canonicalised and now keeps the source order:
`fld dword ptr [ebx + 0x30]` / `fadd dword ptr [ebx + 0x40]` — exactly the original.
`max[1..3]` stay canonical (`fld [ebx+0x44]` / `fadd [ebx+0x34]`, …) and still match.

Equivalent variant that also matches (ndiff=0): the temp **plus** writing
`box.max[0] = m_center[0] + m_halfExtent[0];` (operands swapped in the source).

## What did not work (all kept the canonical order, ndiff=2 at +0xc8)
* Swapping the operands in the source for `box.max[0]` (alone or for all four).
* Parenthesising: `(a + b)`, `((a + b))`.
* `float t = ...; box.max[0] = t;` (the temp is folded back into the member load).
* `box.max[0] = he; box.max[0] += ce;` → right operand roles but 5 instructions instead of 3.
* `a - (-b)` forms → `fld/fld/fchs/fsubp` (4 instructions).
* `+ 0.0f` forms → a real `fadd qword ptr [0]` is emitted (extra instruction).
* Inline/`static` helper `addf(a, b)` → canonicalised after inlining.
* Pointer aliases (`const float* p = he;`) → canonicalised.
* Loops for the min/max block → the min block stops matching (ndiff 8) and the max block is
  still canonical.
* Putting the max block before the min block in the source → the emitted order changes
  (ndiff 58) and the operand order does not flip.
* Temps for all four `min` components → ndiff 4 (indices 2 and 3 flip the wrong way).
