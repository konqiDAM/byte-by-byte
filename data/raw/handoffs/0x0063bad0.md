`else` and `else if` on the id test; the id-fail arm with no `return 0` of its own (shared with the
cast-null return).

Worse:
* early `if (!root) { DAT=0; return 0; }` / `root == 0` / `goto` / `root != 0 ... else` →
  29, extent 533 (VC8 puts the fail inline and moves the shared epilogue into the middle)
* negative id test in any position → 43-56, 553/523 (destroys the exact body)
* `return root` hoisted out of the id test → 43, 553
* id_fail label placed before the null-root block → 22, 529 (the two `return 0` tails merge)

**Conclusion:** the cold-block order is a VC8 layout-pass decision. Statement position, label
position, if/else/goto form, the return expression, `volatile`, and sharing the `return 0` statement
do not move it, and every shape that does move it destroys the exact body or the merged epilogue.
This is the class-5 "position is coupled" pattern (`handoffs\lessons-rival-code.md` §19.5/§18.2).

## What I would try next

1. Give the **null-root block a second incoming edge** (one real extra use, not a "free" one): e.g.
   a second null test on `root` in the cast block that jumps to the same tail, so the layout pass
   sees it as non-cold and traces it before the id-fail block. Watch the instruction count.
2. Make the **id-fail block unmergeable but still last**: put a store through `DAT_010760a4` into
   the id-fail arm (it already has the delete call) or an extra read of the global after the delete
   (§19.33 double read), so the block cannot be placed adjacent to the shared epilogue.
3. `f3check --permute` is forbidden here (hangs, has cost the project two claims). Do not use it.
