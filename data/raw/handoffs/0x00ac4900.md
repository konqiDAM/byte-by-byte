# 0x00ac4900 - TYPE DEFECT: `or ax,0xffff` cannot be expressed under the pack's `unsigned int`

Released 2026-11-12 (best_code kept). **Do not re-claim expecting a match without fixing the type.**

The whole function matches except **one instruction**, at `+0x46`:

```
ORIG   0046  66 83 c8 ff   or  ax, 0xffff      <- writes only the low 16 bits
OURS   0046  b8 ff ff 00 00  mov eax, 0xffff   <- writes the whole register
```

`or ax,0xffff` is 4 bytes, `mov eax,0xffff` is 5 -> our extent is 76 for a 75-byte function. That single byte
is the entire residue; every other instruction in the 75 is byte-identical.

## Why it cannot be fixed from source (measured, not assumed)

`or ax,...` is what VC2005 emits when the result is **16-bit**. The unit already declares

```cpp
unsigned int NiPSysData_CountView::FUN_00c24ea0(void);
```

so changing the definition's return type is rejected:

```
C2556: overloaded function differs only by return type
C2371: redefinition; different basic types
```

Tried and rejected/failed: `unsigned short` return, `short` return with `return -1;`,
`(unsigned short)` cast, `(0 | 0xffff)`, and a 16-bit local (`a3_or`, `a5_local` both stay `mov eax,0xffff`,
ndiff 1, extent 76).

**This is lessons rule L11: a wrong SIZE is fixable, a wrong TYPE is not.** The original function returns a
16-bit value; the pack says `unsigned int`.

**Action for maintainers:** correct the symbol's return type to `unsigned short` (or `short`) and re-span to 75.
**Action for an agent:** none until that changes.
