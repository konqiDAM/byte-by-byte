**New measured fact - why the 297-byte family cannot reach it (a bracket, not a spelling):**
the arg setup `push 1; mov ecx, esi` is emitted immediately after the record home store *wherever that
store is* (baseline 0x81; with the store one statement earlier it is 0x7e and the setup follows it). A
stack store is not reordered with a push (program order is kept), so getting the setup first requires
the store's *statement* to sit **after** the call in program order - and every such shape costs exactly
+8 bytes: extent **305**, frame 0x28 -> 0x2c, `this` spilled into the record slot, because `r` (eax,
the alloc result) must then survive the call. Measured on three families: `arg; ref; call; record = r;`,
`arg; call; record = r; ref;`, and `__forceinline KeepRef(RecordX*& home, RecordX* v, RefX* p)`
(store-first, call-first, and store-as-return-value). MSVC does **not** hoist the late store above the
call (confirmed in the d8 listing: the store stays after the call).
So the residue is **store position vs frame size** - the same class as the sibling 0x00742da0's
store-position-vs-cursor-colour bracket.

Also measured dead: scoping the block (`{ ... }` around decl..append) makes `record` share a slot with
a later temp - the frame drops to 0x24 and every offset shifts (extent stays 297, ~40 diffs).

**What would break it:** a shape where `r` is already in a callee-saved register before the call, so
the late store costs no spill. All four are occupied in the target (ebp=this, esi=ref, edi=rep movsd
counter, ebx=0), so that needs a different whole-function allocation, not a local change.
