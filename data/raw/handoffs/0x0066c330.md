## The measured reason the "set-first gets esi" lever does not apply here

I built micro-tests with the same shape as this function (a `const char*` parameter live across a
call, a `R* r = mk()` local created later, both live across calls) and compiled them with the same
VS2005 SP1 `/O2`:

```
void f1(const char* text,int n){ if(!text) return; R* r=mk(); r->b=n; use(text,0); use(r,0); }
```
-> `push edi; mov edi,[text]` ... `push esi; mov esi,eax` - i.e. **the parameter gets edi and the
later local gets esi, always**, in every one of ~10 spellings I tried (including returning `r`,
extra uses of the parameter on both sides, row dying first, row dying last, parameter as 2 arg
types, guard `text==0` ...). The only case where the parameter got esi was when it was the *only*
value needing a callee-saved register.

That is exactly our candidate's behaviour, and it is the opposite of the target. Two more micro
results sharpen it:

* `const char* label=*(const char* volatile*)&text;` (a genuine, non-merged local copy of the
  parameter, loaded once at the top - the rival's lever) still gets **edi** while the later
  `R* r=mk()` gets **esi**.
* The parameter stays in edi even when it is *used* (passed to a call) before the local's
  definition, and when it dies last.

So in this compiler a 2-value pair like this one has a fixed answer: **the value whose definition
comes later in the IL gets esi**, and every spelling that keeps the bytes keeps the parameter's
definition at +0x05 (it has to be in the register for the `test` at +0x09). The target has the
parameter in esi, i.e. the original's allocator input differed in a way no source spelling I tried
(copy through a local, volatile copy, declaration order, inlined helper, type change, guard split,
guard inversion, Find respelling) reproduces.
