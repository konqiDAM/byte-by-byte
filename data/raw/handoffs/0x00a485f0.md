## The model that explains every variant seen (both sessions)

- The whole loop body is one basic block: 0x30-0x79.
- `esi`=this, `ebp`=target, `ebx`=i, `edi`=`&unk38[i]` (val, lives across the call →
  must be callee-saved; edi is the only one left, so it is forced and always matches).
- Three short-lived webs compete for eax/ecx/edx:
  `base` = `[esi+0x38]` (2 uses, 0x30-0x36 in ORIG), `key` = `[..+ebx*8]` (dies at the
  `push` 0x41), `recv` = `&unk44->map` (dies at the call 0x42).
- ORIG = `base:ecx, key:eax, recv:ecx` (base dies at 0x36, recv reuses its colour and the
  receiver is therefore materialised with `mov ecx,[esi+0x44]; add ecx,0x28` — no copy).
- Every draft we can write gives `base:eax` (or `base:ecx` with the key/val ordered so
  that `s` is hoisted above the key load, which then costs the `lea ecx,[eax+0x28]` copy).
- Per `compiler_tips.md` ("Registers: colouring by cost"): scratch temporaries take
  eax, ecx, edx **in code order**; named locals are coloured by cost; ties go to the value
  referenced first in the source. The base load is a scratch temporary in every spelling
  we can produce, hence eax; in ORIG it behaves like a coloured web in ecx, i.e. some
  value is created before it in the temporary order. Nothing we can write creates that
  extra temporary without adding an instruction.

Conclusions (new facts, worth keeping):

1. **A reference-to-pointer base is worse, not better.** Making `unk38` a `const volatile&` /
   `volatile&` helper parameter makes the compiler materialise `&unk38[i]` with
   `lea eax,[ebx*8]; add edi,eax` instead of `lea edi,[base+ebx*8]`, costs 3 bytes of extent
   (190) and reorders the frame. `Entry*&` and `Entry**` are fine on extent but identical to
   the by-value form.
2. **By value and by reference produce the same colouring.** `ref_only`, `ptrptr` and
   `byval_named_base` all emit the identical block
   `mov eax,[esi+0x38]; mov ecx,[esi+0x44]; mov edx,[eax+ebx*8]; lea edi,[eax+ebx*8]; push 0; add ecx,0x28; push edx`
   — i.e. exactly session 2's `v11` idx 0. Passing the base through an inlined parameter changes
   nothing: for the base, the parameter is not a coloured web, it is still a scratch temporary.
3. So the difference between the receiver and the base is **not** "parameter vs temporary".
   The receiver becomes ecx because `add ecx,0x28` proves it is a `this` value (a reference
   parameter's address is a real web in the IR); the base has no such treatment available.
   The base stays first in the scratch order and therefore always takes eax.
4. The residual gap is a **pure colouring tie**: `base` needs eax *occupied before it* by a web
   that emits no instruction. No source shape tried in ~2,610 variants across three sessions
   produces that. Recommendation stands: hand this to the build-host solver with
   `best_code` = `claims\clm_a4c437f885ed42ee843e\cand.cpp` (extent exact, 5 instructions, one
   basic block) or the v11 `fwd_cv,val` form which additionally gets the receiver byte-exact.

Do not spend more variants on statement order, named bases, receiver spellings or
reference parameters: all four axes are now exhausted (v7-v14, v16).
