## What this is (analysis, after this session's work)

The four loads are the register allocator's **restore batch at the head of the inner-loop
exit block** `[0x26e,0x27e)`; the two `continue` targets (`L_027e`) sit *after* it, so the
batch is only on the inner-loop-exit edge. Both builds contain the same four reloads for
the same four values out of the same four stack slots - only the order differs:

* ORIG: one batch of four, **exactly descending register number** ebp(5), ebx(3), edx(2), eax(0).
* OURS: a batch of three in descending register number (ebx, edx, eax) and then the ebp
  reload **appended at the block end** (0x27a, immediately before `L_027e`).

So ours splits the restore list into `{ebx,edx,eax} + {ebp}` while the original has one
`{ebp,ebx,edx,eax}` list. The instruction DAG is otherwise identical, which makes this a
**backend tie-break in the restore-list ordering** (the brief's `register swap / store sunk`
row), not a source-shape difference - but the one invisible lever it can still respond to is
internal value numbering, i.e. source declaration/definition order. That lever was swept
hard this session (below) without moving it.

## If someone wants to attack it again - the only untried levers I can still name

1. Watch `+0x26e` only: any variant whose stale `ebp` reload lands at 0x26e matches. Use
   `python out\0x00927640\order.py <pack> <file> [more files]` - it prints just the changed
   region, so a batch of 20 shapes is scored and inspected in ~30 s.
2. Make ebp's restore a member of the *batch* rather than a trailing item. The two values
   that behave differently inside the block are ebp (j: reloaded **and** redefined by
   `add ebp,1` in the latch) and eax (cnt cursor: same situation, yet eax *is* in the
   batch), so the split is not "redefined in block". Something distinguishes ebp - most
   likely that its value is the loop-carried copy created in the *preheader*
   (`mov ebp,1 / mov [esp+0x20],ebp` at 0x1df/0x1e6). A source form where `j` has no
   preheader copy at all would need `mov ebp,1` to disappear, which changes bytes - so this
   is probably unreachable from C++.
3. Compiler-flag check (free): `pack.json` says `/MT /O2 /GS /EHsc /Gy`, and every other
   instruction in the 760 bytes matches under those flags, so the flags are right; a
   different build would not be byte-exact for 758 of 760 bytes.
