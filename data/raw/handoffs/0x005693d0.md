1. **The two count / `GetAt(0)` `je` targets**: ORIG `je 0x175` (straight to the loop, threading through the
   phi block); ours `je 0x16f` (into the phi's `xor eax,eax`). The sibling gets the threading because its
   count/p failures *return before the value is computed*; ours fall into the loop. A `int iFormID = 0;`
   initialization does give the threading (`cand_ Y1`, ins_bad 29) but the compiler then materialises

   the immediate — that is the exact 3 bytes ORIG does not have. Next lever: get the count/p edges to skip
   the value entirely (goto/label structure, or the value declared inside a block that the count/p paths jump
   past) without losing the pressure local.

* **`hkVector4 kScaled` must be `__declspec(align(16))` and 16 bytes** — that is what makes the frame

## 4. The residue (40 instructions, two classes)

### 4a. Guard at +0x145..+0x173 — 5 bytes, **the real blocker**

ORIG materialises a ternary and then tests it:

```
149 cmp word ptr [ebx+0x14], 0        ; count
14e je  0x175                          ;  -> the loop (folded)
150 mov eax,[ebx+0xc] / 153 mov ecx,[eax] / 155 test ecx,ecx / 157 je 0x175   ; GetAt(0) (folded)
159..161 call [edx+0x98]               ; t = child->v98()
163 test eax,eax
165 je  0x16f                          ;  -> the *zero arm*
167 mov eax,[eax+0x310]
16d jmp 0x171
16f xor eax,eax
171 test eax,eax
173 jne 0x1c8                          ;  -> return false
```

VC8 SP1 **always** folds this to `cmp dword ptr [eax+0x310], 0 / jne` (11 bytes instead of 16), which is
why every draft is 5 bytes short. Source forms tried, all folded (each verified in the real function and/or
an isolated micro TU — `tmp_micro*.py`): plain ternary; named local; `if/else` both arms; `int v = 0; if
(...) v = ...`; `&&` chain; two-return inline helper; flat early returns; nested ternary
(`(a && b) ? Lookup() : 0`); ternary in the `if`; `!v`; `v > 0`; `unsigned`; `long`; pointer-typed ternary;
reference ternary; `switch`; `volatile` pointer and volatile load; a global-`inline` accessor; the helper
defined after the caller (deferred inline); the helper defined in-class; `bResultTmp`/`iZero` as the false
arm; dead copy of the value; element-address form; `(int)pForm` as the false arm. None materialised it.

Evidence that this is not my source being wrong:

* the same idiom appears **in the same unit** at `0x569670` (the sibling `CellMopp` function, bytes
  `0x56968d..0x56969d` are identical to ours) and at `0x70655c`, `0x4f257f`, `0x8fb89a`, `0x8fb972` — always
  as a *value* merge, never as a folded `cmp`;
* the *count* / *GetAt(0)* failures **are** folded (they jump straight to the loop), so the compiler folded
  everything it could and left only the value phi — i.e. the source really is the shape in §3;
* the matched neighbour `FUN_00565710` contains **no ternary at all**, so its byte-exactness proves the
  *flags* but says nothing about the optimizer.

**Prime suspect: the unit was built with a different 14.00 build (VS2005 RTM `14.00.50727.42`), which folds
this less aggressively.** compiler_tips already says "when SP1 cannot produce a register choice, try RTM
before deciding it is impossible", and `f3check` supports it via `F3CHECK_RTM_ROOT`. There is **no RTM
compiler on this machine** (`C:\f3decomp\vs2008rtm` does not exist; the only `cl.exe` is
`C:\f3decomp\vs2005\VC\Bin\cl.exe`, 14.00.50727.762). Next step: get RTM, re-run the neighbour oracle
(expect byte-identical too — it cannot tell them apart) and then check this function; if the guard and the
scheduling in §4b both fall into place under RTM, this is a `compile_flags`/compiler report with a
byte-exact checkpoint as proof, not a give-up.

### 4b. Scheduling (≈35 instructions) — the v0d4 vtable load

ORIG loads the `v0d4` slot **early**, right after the `kPos.x` store:

```
99 fstp dword ptr [esp+0x34]      ; kPos.x
9d mov edx,[esi] / 9f mov edx,[edx+0xd4]     <-- here
a5 mov [esp+0x38],eax  ...        ; kPos.y / kPos.z copies and adds follow
b9 push &kScaled ... c9 fstp [esp+0x54] ... ; the three scaled stores
df call edx
```

Ours emits the same two instructions immediately before `call edx` instead. Same for `lea ecx,[esp+0x40]`
(ORIG before `fstp [esp+0x40]`), `mov ecx,esi` (ORIG before `fstp [esp+0x3c]`), `add ebx,1` (ORIG right
after the `fld`), and the `kPos.y`/`kPos.z` dword-copy interleaving. These are pure scheduler positions
(loads floating up / may-alias links from the escaped `&kScaled`), i.e. the same "different optimizer"
signature as §4a. Levers not yet tried: making `kScaled`'s address not escape at the store point (e.g. by
building it through a by-value helper), `/Ob1` vs `/Ob2` on a source-level `inline` helper, and computing
`kScaled` through a temporary `hkVector4` copy.
