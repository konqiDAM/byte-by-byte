Slot map (`esp` offsets, ORIG -> ours):

Allocation order, low address first:
```
ORIG: bCombat, pkActor, count, kName, pkProcess, i, pkModel, pkWorld, pkAnim, pkLink, kPosition
ours: bCombat, kName, count, i, pkWorld, pkProcess, pkAnim, pkModel, pkActor, pkLink, kPosition
```
Same *set*, same *sizes*, same total — a **free-list / colouring tie**, the same family as
`0x009bcad0`'s 2-byte residue (ORIG reuses one slot, ours another). The crux: ORIG puts `pkActor`
in `0x14` and lets `pvTarget` alias it; ours puts `kName` in `0x14` and lets `pvTarget` alias that,
which then pushes `pkActor` to `0x30` and permutes five slots.

**What has been tried and is inert or unavailable here:**
* `--solve-slots` does not work on Fallout 3 symbols (project note, still true).
* Declaration order is *not* the driver: our declaration order is proc, world, actor, bCombat, link,
  anim, count, i, model, kName, ... and our slot order is bCombat, kName, count, i, world, proc,
  anim, model, actor — neither forward nor reverse declaration order, nor first-use order, nor
  last-use order, nor use-count order (all four checked numerically against ORIG's map).
* `bCombat` is first in both, and `pkLink`/`pkPosition`/`kInit` land in place in both, so the set and
  the frame are right; only the tie-breaking differs.
* **Measured negative result: declaration order does not move the colouring at all.** Swapping the
  declarations of `ProcessC7* pkProcess` and `WorldC7* pkWorld` produced a byte-identical slot table
  (`exp_769230/v_swap.cpp`). So do not spend a lease permuting declarations — the driver is the set
  of variable webs and their block structure, not the declaration text.
* **Also inert (same byte-identical slot table):** hoisting `ActorC7* pkActor` and `bool bCombat`
  declarations to the top of the function (`exp_769230/vA.cpp`), hoisting `unsigned int i` out of
  the `for` init (`exp_769230/vB.cpp`), and making `~NiFixedString` out-of-line + noinline
  (`exp_769230/vC.cpp`). Exp 3 below (block shape) is therefore the untried lever, together with
  the redundant-name one.
* **A real lead, measured:** ORIG's dword slots are handed out almost exactly in **descending order of
  memory references**: 0x14 has 9 refs, 0x1c 7, 0x18 6, 0x20 5, 0x24/0x28/0x2c 4, 0x30 3, 0x34 2,
  0x38/0x3c/0x40 1 — one inversion only (0x18 before 0x1c). The 1-byte `bCombat` takes the first
  (byte) slot in both builds. Ours gives 0x14 to `kName` (8 refs) because our `pkActor` carries fewer
  memory references than ORIG's 9 — i.e. ORIG re-loads the actor from its home where we keep it in a
  register. So the lever to try first is **making `pkActor` memory-resident / raising pressure across
  the 0x2f0-0x660 region** (§ the "one value live across the chain" law), not declaration order.

**What to try next (ranked):**
1. **The redundant-name lever (§20.22/§20.26)** — the most likely cause. ORIG uses its slots *more*
   than ours (f3check pairs `esp+0x14` with 9 uses, ours 8; `esp+0x18` 7 vs 6): look for one value in
   ORIG that is named twice (`v = f(); n = v;`) or a declared local that only duplicates a
   temporary; adding that one extra web changes the colouring order wholesale. Candidates by ORIG
   use count: `pkActor` (9), `count` (7), `kName` (6).
2. **Block shape (§20.24)** — a nested `{ … }` is a slot-allocation unit. Try wrapping
   (a) the `world`-selection `if/else` and (b) the `pkActor`/`bCombat` block each in its own scope,
   and (c) the `InitC7` block with the `base->unk424` pair block separated.
3. **Two names for the loop bound**: ORIG reloads `[esp+0x18]` in the loop test (a homened
   `count`), which ours also does — but try `unsigned int ItemUpdateArray = pkAnim->GetCount();`
   with the loop on a *second* name (`unsigned int i, n = ItemUpdateArray;`).
4. If the permutation still will not move: the build host's permuter/solver runs on the near miss
   when the claim is given up with `best_code` (§ step 8 of agents.md), and the residue is exactly
   the kind it searches.

## 5. Facts about this function worth keeping (all measured)

* `InitC7` is **0xc0 bytes**, not 0xb0. `esp+0x44 + 0xc0 = 0x104` is what makes `sub esp,0xf8`.
  Its live members: `+0x00/04/08` floats, `+0x80` parent pointer, `+0x88` int 0, `+0x8c` scale,
  `+0x96/97/98` bytes, `+0xac` float. `+0xb0..0xbf` are never referenced.
* `and esp,-16` comes from `InitC7` being `align(16)`; `esp+0x44` is the 16-aligned slot.
* **`new` does not produce ORIG's align adjustment in VC8 14.00.50727.762.** Measured
  (`exp_769230/tnew.cpp`): `new` of an `align(16)` class emits only `call operator new` +
  `test eax,eax / je` and no adjust, with or without a user `operator new`. ORIG has
  `mov dl,al / and dl,0xf / mov cl,0x10 / sub cl,dl / movzx edx,cl / add eax,edx / mov [eax-1],cl`
  and **no** null test ⇒ ORIG is `new (AllocAligned(sizeof(ProjC7))) ProjC7(kInit)`: placement new
  into an inline helper that allocates `n`, aligns to 16 and tags the byte before. That is in the
  draft and matches byte for byte.
* `sizeof(ProjC7)` must be **0x4f0** (`push 0x4f0`). `ProjC7` touches vtable `+0xcc`, `+0x290`
  (a `SubC7`), `+0x294` bits, `+0x3e8` float, `+0x424` pointer.
* `pkCell` must **not** be a local — ORIG re-reads `[ebx+0x3c]` at `0x0056` and `0x0533`.
  Dropping that local took the slots from 2/25 to 19/25 in place.
* `ClipC7::GetCount()` reads the **word at `+0xa6`** (`cmp word ptr [esi+0xa6]`), `GetAt()` is
  `[+0xa0]`, `GetModelFilePath()` is `[+0x18]`, and the model's `NiFixedString` is at `+0x08`
  (the `Actor_AreReferencedValuesEqual` compare folds to `cmp dword [eax+8], kName.text`).
* `F_007348c0` returns **bool** (`test al,al`); `F_0040dff0`/`F_0040c2e0` return int
  (`test eax,eax`). The dialogue block keeps a redundant `ProcessC7* pkHigh = m_pkProcess;`
  (as the twin does) — that is what reuses `esi`.
* `SetProjectile` takes a **refcounting handle by value** (ctor increfs `[proj+4]`, no destructor
  emitted): `push ecx` reserves the arg, `mov [esp+..],esp` spills its address (dead in ORIG).
* The `NiFixedString` destructor is **inlined at the loop tail but called out of line**
  (`0x422950`) on the `continue` path. Our draft inlines both and tail-merges them: that plus
  short-jump encodings is the 33-byte extent gap. Not yet solved; it is the only remaining
  *instruction-level* (not slot) difference.
* The TLS accessor (`mov ecx,fs:[0x2c]; mov edx,[__tls_index]; mov eax,[ecx+edx*4]` then
  `cmp [eax+0x24c],this / [eax+0x248]`) is a `__declspec(thread)` struct with members at
  `+0x248`/`+0x24c`; the draft models it as `GetParent(RefC7*)` and matches.
