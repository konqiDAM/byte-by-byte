## The mechanism map (measured; 130+ variants re-measured tonight)

| count expression computed… | code emitted | position |
|---|---|---|
| **outside** the `if` in a named temp that lives across the branch (`unsigned b = mx*4; if (mx) p = A(b);`) | `lea <reg>,[eax*4]` 7-byte, **fresh register** | scheduler **hoists it above the `jbe`** → ndiff 3 (only reg/order wrong) |

So the two ends are different compiler paths, exactly the "position and colouring are coupled"
class — but the *form* (lea vs add/add) is the real discriminator, and it is decided by whether
the scaled value has its own register home.

load* gives add/add.

```cpp

// G(this->mx * 4)          with mx a MEMBER LOAD            -> add eax,eax ×2 + push eax
```

## The open question for the next agent (one sentence)

**Find a source form where the then-block's scaled count gets a register home (non-destructive
multiply) although it has no later use.** Read "The decisive test" below first: that section proves
this cannot come from liveness (the original has no stack frame and no free callee-saved register),
so the door is *not* "make the count live past the call".

A `__forceinline` forwarder whose *count parameter* is used twice (the null test **and** the multiply) is the strongest remaining candidate: it is the one
construct that can give a parameter a home without adding code. The version tried tonight
(`out\0043eb00\w1\v12.cpp`, 3-param forwarder, `if (n==0) return 0;`) produced the right branch
shape but restructured the whole block (extent 153, ndiff 47) **and still emitted add/add in the
then-block** — so refine it: keep the copy loop and the else `p = 0` at the *call site* and inline
only `allocate-and-scale`, e.g.

```cpp
static __forceinline void* AllocScaled(unsigned n)   // n used by nothing else
{ return FUN_0089e810(n * 4); }
...
if (m_uiMaxSize > 0) { m_pBase = (void**)AllocScaled(m_uiMaxSize); /* loop */ } else m_pBase = 0;
```
(tried as `w1\v15` = ndiff 11, add/add — so the parameter alone is not enough when the body's
parameter is substituted; the *two uses inside the inlined body* are what matter, and the helper
must therefore contain the `if`. Reconcile that with the block shape: the helper must contain the
test but not the stores, so the caller keeps `mov edi,[esi+4]` / the two stores before the branch.)

Other untried levers, cheapest first:
1. `_ReadWriteBarrier()` between the two stores and the alloc (pure scheduling barrier, no bytes).
2. A genuinely *double* read of `m_uiMaxSize` inside the then-block (`n1 = mx; n2 = mx;
   p = A(n1*4);`) — the double-read law keeps the value live past the multiply.
3. Force the count a memory home: `unsigned b = mx*4; unsigned* pb = &b; ... A(*pb);` (adds a slot,
   only worth it if extent still lands on 151).
4. The **register** end in isolation: with the v09 shape the allocator picks ecx; the original picks
   edx. If a form is ever found that keeps the lea after the `jbe`, expect the register to flip to
   edx for free — do not chase edx separately.

## The decisive test (t6/t9, run last)

A `__forceinline` helper is **not** inlined when it contains a loop, so `t6\d01.cpp` shows the
*uninlined* callee with the count as a real parameter used **three times** (test, multiply, loop
bound):

```
test esi,esi | jbe | lea eax,[esi*4] | push eax | call A      <-- target shape, in one place
```
i.e. `lea` after the branch happens **exactly when the count must survive the `call`**.
Copied into `P::f` (`t7\x01.cpp` / `x04.cpp`) it reproduces the target shape but at the cost of
`push ebx` + `test edi,edi`/`jbe` before the copy loop → extent grows, no match.

**The proof that closes this door:** the original has **no stack frame** (`push esi; push edi`,
no `sub esp`) and **saves no callee-saved register beyond esi/edi** (`edi` holds `saveBase`,
`esi` is `this`). Therefore the count value *cannot* survive the call in the original. So the
original's non-destructive multiply was **not** chosen by liveness — and every source shape whose
count dies at the multiply produces `add eax,eax;add eax,eax` (measured: 96 spellings in
`t4`, plus `t5` (conversion wrapper, `void*`-typed allocator parameter, pointer casts),
`t9` (which member is tested vs multiplied, guard helpers, loop bound = the count),
`t10` (pointer/`reference` to the member, `*(&mx)`)). Copies of the member, `const&`, `unsigned*`,
and the guard-helper-with-loop-outside all collapse to `add/add` too.

So: the residue is **not reachable from the interior of the conditional block** with this
compiler. And `_ReadWriteBarrier()` is now **tested and dead** (`t11`, needs `#include <intrin.h>`):
placed before the count it forces `cmp DWORD PTR [esi+8],0 / jbe` (a reloaded compare) instead of
`test eax,eax` — the flag chain across the two stores is lost, so the branch is wrong; placed after
the stores it leaves `lea ecx,[eax*4]` *before* the `jbe` (w04). It cannot buy the position without
losing the flags.

Two doors remain open, both cheap:
1. Anything that makes the **branch's flag producer land after the stores** — the original's
   `test eax,eax` at 0040 followed by two `mov` stores and then `jbe` is a *flag chain* through
   stores, which means the `test` was emitted by the null-check pass (not by the store). A source
   that emits a *second* test (e.g. the double-read law giving a null test per read) would let the
   `lea` be scheduled after the second test/branch without touching the flag chain.
2. Get the multiply **outside** the block while the branch still precedes it — i.e. keep the v09
   temp but find any reason the scheduler must sink it. Not found tonight: 36 permutations of the
   store order / temp source (`mx` vs `sz` vs `es`) / condition (`mx`/`sz`/`b`) in `t12` **all**
   emit `lea ecx,[eax*4]` *before* the `jbe`; register-pressure experiments (making ecx *and* edx
   busy across the branch) are the one untried variant of this door.

# Addendum 2026-11-13 10:05Z — linkage/alias lever: dead; operand-node class is the real rule

## 1. §19.57 linkage lever — closed, with proof

* The function has **no file-scope data symbol** (no global, no DAT_) — nothing whose alias
  set a `static` could shrink. The two stores before the branch are plain `this`-relative
  member stores and they already match byte-for-byte.
* The only file-scope names are the callees. Neither is in the pack headers, and the unit
  declares `FUN_0089e810` only at unit line 34207 (another TU). `static` on it is refused:
  `error C2129` (measured: `out\0043eb00\p3\st.cpp`). A local stub body would move the call
  target bytes that are correct today.

## 2. The real rule (this is the new, reusable finding)

All 15 sites in the image with `lea reg,[eax*4]; push reg; call FUN_0089e810` take a
**non-leaf** multiply operand: `movzx` of a 16-bit field (0x007fb73c, 0x0083411c,
0x0077a7ec, 0x00ab8387, and 0x00555790 in our own unit), a load through an escaped member
pointer (0x0085f74f, 0x0085fd2f, 0x008cc7be, 0x00863c9d), a spilled-local reload
(0x00827084, 0x009e4f28), or a phi (0x008b95cc). Never a direct member load.

Probe `out\0043eb00\p3\r.cpp` (one compile, `win_tools\msvc9.py /c /FAcs /O2 /MT`) shows the
rule from the other side — a call-return operand reproduces the target exactly:

```
void Q::t7() { unsigned n=cap; n=(unsigned)Opaque(&cap); if(n) b=(void**)A(n*4); else b=0; F(0); }
0000c  85 c0      test eax,eax

0001a  51         push ecx
```

whereas every leaf operand (member load t1..t6, t9; pointer local; `volatile` reload;
inlined getter) gives `add eax,eax; add eax,eax`.
