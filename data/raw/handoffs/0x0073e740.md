## NEW: exact frame arithmetic — ORIG's slot is 16-byte aligned, ours is not

Frame is `sub esp,0x3c` + `push ebx/esi/ebp/edi`, so the local frame base is `ESP0-0x3c`
(slot offset = address - ESP0, which is exactly what /FAs prints as a negative number):

| site | source | pending pushes | ours disp | ours slot | ORIG disp | ORIG slot |
|---|---|---|---|---|---|---|
| +0x46e | `height = actor18->v16c().z` | 0 | 0x1c | **0x0c** | same | **0x0c** |
| **+0x5e7** | **`package14->FUN_005a53d0(actor18)`** | 12 | 0x34 | **0x18** | 0x3c | **0x20** |
| +0x733 | `height2 = actor18->v16c().z` | 0 | 0x34 | **0x24** | same | **0x24** |
| +0x755 | `package14->FUN_005a53d0(actor18)` discarded | 4 | 0x44 | **0x30** | same | **0x30** |

So the two live questions are not "which slot is reused" but:

* ours:  temp area `0x0c, 0x18, 0x24, 0x30` — four contiguous 12-byte slots, frame `0x3c`, tight.
* ORIG:  `0x0c, **0x20**, 0x24, 0x30` — an **8-byte hole at 0x18..0x1f** and an 8-byte overlap of the
  0x20 slot with the 0x24 slot (legal: disjoint live ranges, different branches).
* **ORIG's 0x5e7 slot is 0x20 = 16-byte aligned; ours is 0x18 = 8 (mod 16).**

**The same signature is in the other open function of this class, 0x007641c0** (`progress\0x007641c0.md`):
ours `0x08` / ORIG `0x10` — again an 8-byte hole, again **ORIG 16-aligned, ours 8 (mod 16)**, again
exactly 8 bytes. Two independent functions, same rule: *the `FUN_005a53d0` sret temp sits at a
16-byte-aligned frame offset in the original*. Also consistent inside this function: ORIG's other
`FUN_005a53d0` temp (+0x755) is at 0x30, which is already 16-aligned; the two `v16c()` temps
(a different 12-byte type) are at 0x0c/0x24 and need no alignment.

**Why the obvious fix cannot be used:** a 12-byte C++ type can only have alignment 4 (size must be a
multiple of alignment), and every type that *does* carry 16-byte alignment grows `sizeof` to 16,
which changes the frame (measured below). So the alignment cannot be expressed from the source
declaration — it is a c2 frame-packer decision.

## The "last-use / slot reuse" lever the brief asked about — tested and NOT applicable here

The lever was: "the sret temp reuses the slot of the most recently dead local of the same size, so
move that local's last read next to the call". In this function there is **no 12-byte named local
anywhere** — the only 12-byte objects are the four hidden temps themselves, and three of them are
pinned byte-identical by the match. Site 1 (`v16c()` at +0x46e) is the only 12-byte temp that dies
before +0x5e7, and it lives in a *different branch* of the same `if/else if` chain; dragging its
final read down to +0x5e7 would rewrite the matched bytes at +0x46e..+0x49x. A dummy read is
eliminated (measured above, 8-byte dead locals). **So the lever has no handle in this function —
it is not that it failed, it cannot be expressed.**
