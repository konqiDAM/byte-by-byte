## Hypotheses / next steps (priority order)
1. **The one missing piece is the 2-byte `mov eax,ecx`.** With the EffectShader-member accessor
   the load is folded but MSVC coalesces the load straight into the select's phi register
   (eax). The original kept the loaded value in a separate scratch (ecx) and copied it into the
   phi. That is a *return-value materialisation* of the inlined accessor. Things worth trying:
   * make the accessor return through something the inliner cannot coalesce — e.g. a body whose
     return expression is a **`BSString` conversion operator** invoked on a const reference
     (I could not bind a non-const `BSString&` inside a const method; try `const BSString&`
     *plus* a second field read after it, e.g. an `sLen`-based branch that the optimiser removes);
   * an accessor that takes the texture as a **`const TESTexture&` parameter of an
     EffectShader member** (this stays in eax, the parameter forces a second address);
   * a 2-level inline chain (EffectShader member → TESTexture member → BSString member) where
     the middle frame's `this` is a *value* rather than a subobject address.

## Mechanism (why the copy exists in the original)
Block 2 (`+0x244`, fill texture) is the same `?:` and reads `mov edx,[esi+0x30] ; mov eax,[edx+0x150]`:
the phi coalesced with the load because the **base sits in edx** and stays live across that block.
Block 1 (`+0x1ce`) has the **base in eax**, and the original resolves the conflict by loading into **ecx**
(scratch rotation #2 after the base = scratch #1) and copying into the phi **eax**. In every spelling we
can reach, SP1 instead folds the load into the base register (`mov eax,[eax+0x15c]`), i.e. it reuses the
base's register for the destination because the base is dead at that point. To reproduce the original, the
base value at `+0x1ce` must stay live **one instruction past** the load.
