Four classes of difference had to be fixed, in this order:

1. **EH frame** (`eh`). With a plain body VC8 emits `push -1 / mov eax,fs:[0] / __ehhandler` and an
   out-of-line `~hkArray`, because the indirect `node->m_init()` may throw while the local array is
   alive. ORIG has no EH frame ⇒ **the enclosing function is `throw()`**. Measured on a mini TU:
   `throw()` on the destructor, or an exception spec on the function-pointer type, does *not* remove
   it; only `throw()` on the enclosing function does.
2. **Instruction order**. ORIG materialises `mov edi, offset DAT_0116932c` at `+0x10`, *before* the
   three array-ctor stores at `+0x15`. Fix: declare `Node** link = &DAT_0116932c;` before the local
   `hkArray`.
3. **Tail shape and callee-saved colouring — one change** (register allocation + instruction order).
   The unlink arm must advance `node` itself:
   ```cpp
   node = node->m_next;
   (*link)->m_next = 0;
   *link = node;
   ```
   This yields ORIG's 4-instruction tail `mov ecx,[edi]; mov esi,[esi+4]; mov [ecx+4],ebp;
   mov [edi],esi` **and** the colouring `link = edi`, `i = ebx`. `node = node->m_next` makes `next`
   the loop variable's own web, so it coalesces into `esi` and `node` is rematerialised from `*link`;
   that extra `*link` use is what outranks the retry counter for `edi` (same family as lesson 19.91:
   an invariant pointer load beats a counter). Any other spelling (`node->m_next = 0`, a named
   `next`, `node[-1].m_next = 0`) leaves `next` in `eax`, reloads node into `ecx`, and gives `edi` to
   the counter.
   Note the previous draft (`node->m_next = 0; *link = next; continue;`) was also **wrong code**: it
   left `node` on the removed node, an infinite loop.
4. **Import binding** (`symbol_problem`). ORIG's operand is exactly `[0xd9b080]`.
   `__imp__TlsGetValue@4` is **ambiguous** in `f3decomp_symbols.json` — it maps to 0x00d9b080 *and*
   0x00d9b0a4 (alias pile) — so `Bindings.canonical()` returns None and f3check substitutes the
   synthetic `0xe0001000`. A `__declspec(dllimport) TlsGetValue` declaration can therefore never
   match. The only name binding uniquely to 0x00d9b080 is `_DAT_00fdf044`, so the array's destructor
   calls the IAT slot through
   `extern void* (__stdcall* const _DAT_00fdf044)(unsigned long);`.
   **Report this** — two functions in this unit call `TlsGetValue` and both are blocked by it.

## What did not work

* `__forceinline ~hkArray()` without `throw()` → EH frame, out-of-line dtor, every slot shifted 0x14.
* `throw()` on the dtor only, `throw()` on the pointer type, `__declspec(nothrow)` on the member →
  EH frame stays (C2495 for the last one).
* `int i;` declared at function scope; `for (i = ...)`; erase through a named `last` temp; two
  statements `*link = next; node->m_next = 0;` — all leave `link` in `ebx` and `i` in `edi`.
* `(*link)->m_next = 0` with a named `next` (v3/t1): fixes the colouring but leaves `next` in `eax`
  instead of `esi` — same length, 2 bytes off.
* `node[-1].m_next = 0` (n=91) — shorter and wrong colouring.
