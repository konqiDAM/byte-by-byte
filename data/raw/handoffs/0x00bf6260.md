## Hypotheses / next steps

1. **Keep `fst` (non-popping) while starting the pair earlier** (the a6 lead). In ORIG the value stays
   in st(0) from 0x11e through the loop entry (the loop body does `fld st(0); fsub [esp+0x54]`), which
   is what pins it to the pre-loop block. If a source form computes startX before the position copy but
   still lets the compiler keep the value in st(0) (no `fstp` + reload), the extent stays 696 and the
   slot is ORIG's. Try: startX before SetPosition but *with* an extra later use that forces the value to
   stay live in st(0) (e.g. an unnamed temporary feeding both), or a `Vec` copy that keeps cursor.x
   addressable only later.
2. **A same-file callee body** (compiler_tips "Escape"): `Shape::SetPosition` is declared in the pack but
   its body is only the inlined `position = v`. If the ORIG saw a *different* body (e.g. one that also
   touched another member) the may-alias links around the pos stores change without changing the emitted
   stores. Cheap to test: give `SetPosition` a body that reads one more member before storing.
3. **Spot B is a colouring flip**: ORIG's `c` web is al from the switch onward, ours coalesces `c` with
   `ch` (bl) and pays a copy at the merge. Every spelling I tried normalises. Try forcing a separate
   web with an aliasing point (take `&c` once, or pass `c` by reference to an inline helper) -- expect
   the copy to move to the head, extent must stay 696.
4. Do **not** re-run statement-order permutations of `startX` / `*width = 0` / `SetPosition`: they are
   all byte-identical to the draft (see b7). The residue is not order-sensitive.
5. The open `pack_problem` report on this function's neighbours (0xbe0a80 span, 0xbe0c1a jump target)
   does **not** look related: this function is 696 bytes and its extent matches exactly. If triage ever
   reproduces a boundary problem for 0xbf6260, re-check these two spots before believing them.
