## 5. Why (codegen explanation)

1. **The prologue read placement and the register swap are the same problem.** `push reg; mov
   reg,[esp+0xc]` can only be emitted when the allocator gave that parameter the register pushed at
   that point. Family B gives `edi` to owner and `ebp` to arg; `edi` is pushed fourth, so the loads
   must use the post-prologue esp (`[esp+0x18]`/`[esp+0x14]`) and land after all four pushes and
   after the first call. There is no separate "prologue timing" bug to fix â€” fix the colouring and
   the four prologue diffs disappear with it.
2. **What flips owner vs a:** anything that names the allocator (`Heap* heap`, `Heap& h`, a named
   `unsigned long idx`) adds one more value used in each allocator block, which perturbs the
   per-block cost (`uses Ã— P Ã— frequency`, live-through blocks subtracting) and moves `owner` ahead
   of `a` in the colouring order. Measured, repeatedly: named allocator â†’ `owner=edi, a=ebx`
   (family B, `an_e1`, `an_s7`); no named allocator and no named index â†’ `owner=ebx, a=edi`
   (family A, `an_ckpt`, `an_s6`).
3. **Why the parameter copies must come first:** the copies are `volatile` reads through a
   pointer to the parameter's stack slot. A call intervenes, and the compiler may not move an
   address-taken volatile read across it, so with the tls call first in the source (family B) the
   reads sink *below* the call. Put them first (family A) and they are placed in the true prologue â€”
   which is exactly what the original does, byte for byte at `+0x000`â€¦`+0x009`.
4. **Why the allocator's constant pushes hoist:** with the allocator in one expression the two
   `push` stores are independent of the tls result, and the scheduler emits them as early as it can
   (before `push eax; call esi`), which the original does not do. Any named local for the allocator
   keeps the statement split and the pushes stay after the call â€” but that is the same construct
   that breaks the colouring (point 2). The two effects are tied to *one* source decision.
5. **Why not just drop the volatile copies:** without them (natural source) VC8 CSE's the size
   constant into a callee-saved register (`mov ebp,0xc`, then `push ebp` and `mov word [eax+4],bp`)
   because the constant has four uses and the parameters only two, and the parameters stay in memory
   and are loaded late (`mov ebx,[esp+0x14]`). Result 277 bytes, 22 slots. Making the size `sizeof(A)`
   (`an_s4a`, `an_s4b`) does **not** stop the CSE (measured: still 277/22). The original
   re-materialises the immediates at all four sites precisely because `ebp` is occupied by the
   parameter.

## 12. The prologue model (2026-11-11 18:55 UTC) - supersedes the "rotation" story of section 11

### 12.1 What the three families look like

```
ORIGINAL                          P-direct (no volatile copies)     P-split (named i0 + volatile copies)
+0x000 mov eax,[DAT_010f3170]      +0x000 mov eax,[DAT_010f3170]      +0x000 mov eax,[DAT_010f3170]
+0x005 push ebx                    +0x005 push ebx                    +0x005 push ebx
+0x006 mov ebx,[esp+0xc]  owner    +0x006 push ebp                    +0x006 mov ebx,[esp+0xc]  owner

+0x00b mov ebp,[esp+0xc]  arg      +0x008 mov esi,[DAT_00d9b080]      +0x00b mov ebp,[esp+0xc]  arg
+0x00f push esi                    +0x00e push edi                    +0x00f push esi
+0x010 mov esi,[DAT_00d9b080]      +0x00f push eax                    +0x010 mov esi,[DAT_00d9b080]
+0x016 push edi                    +0x010 call esi                    +0x016 push edi
+0x017 push eax                    ...                                +0x017 push eax
+0x018 call esi                                                    +0x018 call esi
```

* **P-direct** = `exp91\main28\d_plain.cpp`: index load at +0x000, but the parameters are *rematerialised*
  from their incoming slots (+0x021, +0x07f) instead of being promoted into `ebx`/`ebp` in the prologue.
  Its **downstream is the original's, instruction for instruction** (load2 -> `ecx`, `push ecx`,
  `mov edi,eax` sunk to just before the `tls` call, load3 -> `edx`).
* **P-split** = `exp91\main23\s_sp1_mix1.cpp`, `exp91\main24\q_q2.cpp`: the prologue is byte-identical to
  the original, but the store of `a` is not sunk, so load2 takes `eax` (5-byte `A1` form) and the extent
  drops to 277.
* **P-vol** = `claims\best2_0x00902620.cpp` (ndiff 2): the parameter promotion is right, the downstream is
  byte-identical from +0x017 to +0x115, but the index load sits at +0x00a.

### 12.2 The rules, all measured

1. Entry-block instructions are interleaved into the prologue **in source order**.
2. A **volatile read of a parameter slot orders later loads after it** -> the index load reaches +0x000 only
   if it is created *before* the two volatile parameter reads.  Proof: `exp91\main28\d_plain.cpp`
   (plain copies, load at +0x000) vs `exp91\main28\d_vol.cpp` (volatile copies, load at +0x00a).
3. **Loads float up.**  Proof: `exp91\main33\w_if_only.cpp` - the index load floats to +0x001, ahead of
   every register save, when nothing blocks it.
4. Only a **volatile local copy of a stack parameter** produces the classic prologue promotion
   (`mov ebx,[esp+0xc]`).  Proof: `exp91\probe1.cpp` T1/T3/T4 compiled with the real VC8.
5. **Call arguments are evaluated right-to-left**; an inline helper's parameters are *bound* in the call's
   source order.  The two orders disagree, which is why helper shapes fail.
6. The original's three index loads are **anonymous scratch temporaries** (compiler_tips: scratch temporaries
   take eax, ecx, edx in turn, in code order) - the original shows exactly eax, ecx, edx.  So the first index
   load **cannot be a named variable**; the P-split family is therefore structurally wrong.

### 12.3 The contradiction

The index load must be an anonymous temporary created before the volatile parameter reads; a temporary is
created where it is used; its use is the `tls` call, which is after the reads.  A named variable survives that
but is not a scratch temporary, so loads #2/#3 lose the eax/ecx/edx rotation.


## 13. The decisive diagnostic (2026-11-11 19:40 UTC)

`exp91/main36/z_plain_last.cpp` vs `z_vol_last.cpp` - identical shape, only the parameter copies differ
(plain vs `*(T* volatile*)&p`).  The index is the **last** argument of the call, so with MSVC's right-to-left

**A volatile operation is a scheduling barrier for every load in the block, regardless of creation order.**
The original's index load is at +0x000, so the original contains **no volatile read**; but the only construct
that produces the original's classic prologue promotion is a volatile read of the parameter slot
(`exp91/probe1.cpp` T1/T3/T4).  The two requirements are mutually exclusive in every source form tried.

## 15. The comma trick (2026-11-11 19:10 UTC)

`exp91/main48/y_plaincomma_m1.cpp` (= `claims/best_perfectprologue_0x00902620.cpp`):

```cpp
mem = (iv = *(volatile unsigned long*)&DAT_010f3170,
       o  = *(Owner* volatile*)&owner,
       v  = *(void* volatile*)&arg,
       AllocMem((Heap*)tls(iv), 12, 0x22));
```

gives a **byte-perfect prologue** (+0x000 `mov eax,[DAT_010f3170]`, +0x006 `mov ebx,[esp+0xc]`,
+0x00b `mov ebp,[esp+0xc]`, +0x018 `call esi`) - the first source form that satisfies both requirements
(the index load in the entry block *and* the parameters promoted in the prologue).

Why it works: the comma operator evaluates left to right, so the volatile index read is created **before**
the two volatile parameter reads, and a volatile read cannot be sunk to its use, so it stays at the head of
the basic block; the scheduler then keeps the three in that order.

Remaining difference: the copy of `a` is not sunk past the second allocation's index load, so `eax` is free
when load 2 is scheduled and load 2 takes `eax` (5-byte `A1`) instead of `ecx` (6-byte `8B 0D`) - ndiff 25,
extent 277.  In the no-promotion family (`exp91/main39/v_after_alloc_m1.cpp`, ndiff 4) the copy *is* sunk and
load 2 gets `ecx`, exactly like the original.

## 18. The promotion is liveness-driven, not first-use-driven (2026-11-11 20:05 UTC)

From `exp91/gamecode_promotion_report.md` (all 222 classic promotions in 0x009xxxxx compared between the
pack's source and the image):

* 200 promote a parameter that is used before the first call;
* **4 promote a parameter whose first use is after the first call** - two of them genuine
  (`0x00933a20`, `0x009b4940`);
* the reason is **liveness across a call**: the parameter must survive the call, so it is copied into a
  callee-saved register, and the copy is placed as early as the call requires.

In `0x00933a20` the first call follows the prologue immediately, so the copy is in the prologue; the late
alternative (`push dword ptr [esp+0x10]`, 6 bytes) would have been larger than `push edi` (2 bytes).

=> For our function the parameters are live across the `tls` call, so the copy belongs in the prologue - but
VC8 puts it late because the incoming slot is still readable there and the size is unchanged.  The lever is
therefore to make the late copy impossible or more expensive.

Sub-agent verdicts: no zero-instruction use of a parameter promotes it (about 100 constructs compiled with the
real VC8, `exp91/probe1..9.cpp`); no expression form threads the index temporary to the `tls` call without
either a second load or a named carrier (which breaks the eax/ecx/edx rotation).

## 23. The homing rule and the paradox (2026-11-11 22:15 UTC)

The rule (proved with ~25 real compiles, `exp91/PROLOGUE_HOMING_RULE.md`): a stack parameter is loaded
in the entry block iff it is COLOURED into a callee-saved register AND some use of it is reachable
without executing a call; a load is never hoisted above a call, so otherwise it sinks to the first
use.

The arithmetic: homing costs 6 bytes once and saves 3 per pushed-argument use or 2 per register use -
break-even at 2 pushes or 3 register uses, and the -16 stack-parameter penalty means a parameter needs
MORE than break-even.  **Our `arg` (2 pushes) and `owner` (3 register uses) are both exactly at
break-even, which is why the house idiom rematerialises them.**

The paradox: the original's parameter loads are ABOVE its first call, which the rule forbids, and the
machine code shows no use of the parameters before that call - so the original's source must have had
one, or the original was built by a compiler whose scheduler hoisted those loads.  With the index
load needing to be both first and anonymous, the three requirements remain mutually exclusive.


## 24. The last blocker is a scheduling rule (2026-11-11 22:50 UTC)

`claims/best_bodyexact_0x00902620.cpp` (ndiff 2, extent 278) has the parameter homing in the
prologue AND everything from +0x033 byte-identical to the original - including the second index load
taking ecx and the copy of `a` sunk past it.  The trigger: **the first index read must be an unnamed
plain temporary** (a named value is coloured and consumes no scratch-temp slot, which rotates the
second load into eax).

What is left is one instruction slot: the plain first index read lands at +0x00a because **SP1 emits
volatile reads before plain loads in a scheduling region**, and it cannot be hoisted above the two
volatile parameter re-reads; making it volatile pins it at +0x000 but breaks the rotation.


## 25. The index load CAN be first, and what it costs (2026-11-11 23:15 UTC)

A volatile read of the index into a named local, placed first, puts `mov eax,[DAT_010f3170]` at
+0x000 AND keeps the value in the anonymous scratch temp eax (`push eax` at +0x017), with the body
byte-exact from there: `exp91/main110/s_ulong_plain_ov_1.cpp`, `exp91/main111/t_idxvotls_cast.cpp`,
`exp91/main113/*` (extent 277).

What it costs: the colouring swaps `owner` (ebx -> edi) and `a` (edi -> ebx).  Hypothesis: the index
statement raises P (values used in the entry block), which favours `owner` (all 3 uses there) over `a`
(1-2 uses there); in the original `owner` is a homed stack parameter and carries the -16 penalty,
which is what lets `a` win edi.

So the three-way conflict recorded in section 24 is now a **two-way** one: the index load can be
first, and the parameters can be homed (volatile), but the colouring then differs.  The open question
is whether the colouring can be restored without changing the emitted code.


## 26. FUN_00a35760: homing with a post-call first use, and why (2026-11-11 23:35 UTC)

`FUN_00a35760` homes its 4th parameter at +0x006 (interleaved with `push esi`) while its first use is
at +0x011, *after* the first call - the exact shape that looked impossible for our target.  Its uses
span the two arms of an if/else (two blocks), so the home load is hoisted to their common dominator,
the entry block, and therefore above the call.

So the placement rule is: the single home load of a coloured parameter sits at the top of the block
dominating all its uses; one block -> at the first use; several blocks -> hoisted to the dominator.
Our target's parameters are used only in the entry block, which is why the plain route cannot hoist
them, and the volatile route is the only way to define them at the top - at the cost of the
scheduling barrier and of the unpenalised-copy colouring.


## 27. The closed loop, in cost terms (2026-11-11 23:55 UTC)

With cost per block = uses x P x frequency and a -16 stack-parameter penalty, `a` keeps `edi` while
P_e < 2.5 P_b (P_e = values used in the entry block, P_b = in a release-check arm, frequencies 1 and
0.5).  best2 sits exactly on that boundary; the volatile index read adds one value to the entry block
and tips `o` over `a`, giving the observed owner=edi / a=ebx swap.

So the requirement is: the index read must be volatile (emitted first) yet must not count as an entry
block value - i.e. an anonymous scratch temporary - and a volatile read can only be anonymous as a
direct call argument, which puts the call after it and the parameter loads out of the prologue.  That
is the closed loop.  The only known escape is multi-block uses of the parameters (FUN_00a35760), and
the target's first branch is at +0x0bb, after all of their uses.

600 variants today (main108-117) plus f3check --permute: none beats ndiff 2.


## 28. The colouring rule and the second Pareto point (2026-11-11 23:50 UTC)

Measured over ~195 compiles: when the TLS index load is forced to +0x000 with a volatile read, the
`owner`/`a` swap is controlled by the number of ENTRY-BLOCK uses of the coloured copy `o`.  Three
uses (`ooo`) -> o takes edi, a falls to ebx.  Two uses (`woo`, i.e. the first owner call written
against the parameter) -> a keeps edi and owner gets ebx, i.e. the original colouring, with the index
load still at +0x000.

`claims/best_idx0_ownerebx_0x00902620.cpp` is that source: the whole first block is byte-identical
through +0x032.  The only remaining difference is at +0x033, where the copy of `a` is scheduled
before the second index load and therefore the load takes the 5-byte `mov eax,[G]` form instead of the
6-byte `mov ecx,[G]` form; the extent is 277 and the tail cascades.

The pair of Pareto points (addendum 25) shows the requirement precisely: P1's body is right because
its first index read is an anonymous temp (the copy of `a` sinks past the second load), P2's prologue
is right because its index read is volatile; an anonymous volatile temp exists only as a direct call
argument, which forces the call - and the parameter loads - after the index read.


## 29. The complete mechanism (2026-11-12 00:00 UTC)

Three measured rules close the model:

A. `push reg; mov reg,[slot]` is one adjacent pair iff the value is materialised at function entry
   (a volatile view does that; a plain copy is rematerialised at its first use).
B. `x = call()` copies eax into x's home lazily (after the pushes, before the call) when the call's
   argument was a BARE LOAD in the call expression, and immediately after the definition when the
   argument came from a named local.
C. A volatile read may not move across another volatile read, and a non-volatile load may not be
   sunk below a volatile read - so the index load is at +0x000 only if its read is the first memory
   access in the source.

The three requirements conflict pairwise (see the handoff addendum 26 table): index-first forces a
named local, which forces the immediate copy (B), which breaks +0x033; a deferred copy forces a bare
load (B), which is then scheduled after the volatile parameter reads (C), which breaks +0x000; and
the parameter loads themselves need the volatile views (A) that cause (C).

Two stable attractors, ~825 compiles: ndiff 2 (index 5 bytes late) and ndiff 25 (first 0x33 bytes
exact, then one byte early).  No source escapes them under SP1.
